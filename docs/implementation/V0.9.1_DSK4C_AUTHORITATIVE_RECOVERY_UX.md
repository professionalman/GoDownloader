### 2. Canonical Mapping

`ROADMAP.md` Milestone `DESK-2 — Lifecycle / Packaging` specifies:
> *"Tray/background/quit, opt-in autostart, recovery UX, support bundle, installer fixtures and web-mode fallback."*

Slice `DSK-4C` implements the Authoritative Recovery UX:
1. Surfaces truthful facts produced by the **existing** durable startup recovery system (`recover()` in `internal/job/recovery.go` and `reconcileFinalizationJournal()` in `internal/job/finalization.go`).
2. Does **NOT** create another recovery engine, second recovery layer, or runtime recovery service.
3. Exposes an immutable per-process `RecoverySummary` and typed `RecoveryIssue` DTO via the shared `jobs` transport domain across desktop (Wails IPC) and web mode (`GET /api/v1/jobs/recovery-summary`).
4. Implements an accessible, non-blocking `RecoveryBanner` in the React frontend with deduplication and distinct success/warning visual semantics.
5. Preserves all critical invariants: StateSync protocols and monotonic cursors remain completely untouched; no localhost HTTP listeners are spawned in desktop mode; no database acknowledgment tables or cross-launch recovery history tables are created.

### 5. Actual Startup Recovery Ownership

Startup recovery execution is strictly owned by `Manager.StartBackgroundTasks(ctx)` invoked during `app.App.Start(ctx)`:
```
App.Start
    -> Manager.StartBackgroundTasks(ctx)
        -> m.recover(ctx)
            -> m.reconcileFinalizationJournal(ctx, &summary)
            -> m.recoverJob(ctx, j, &summary)
            -> m.recoverySummary = summary.Clone() [FROZEN]
        -> ResourceGovernor reconstruction
        -> Stale workdir & queue cleanup
        -> Scheduler.Start(ctx)
        -> Progress Monitor.Start(ctx)
```
- `job.NewManager(...)` creates the struct and registers engine dependencies; it does NOT execute recovery.
- Recovery and summary capture remain firmly in the `StartBackgroundTasks` startup lifecycle, preceding the start of the scheduler and resource governor.

### 6. Final RecoverySummary & RecoveryIssue Contract

Defined in `internal/job/recovery_summary.go` and mirrored in `web/src/types.ts` and Wails TypeScript bindings:

```go
type RecoveryIssueKind string

const (
    RecoveryIssueInterruptedMedia             RecoveryIssueKind = "interrupted_media"
    RecoveryIssueFinalizationFailed           RecoveryIssueKind = "finalization_failed"
    RecoveryIssueEngineUnavailable            RecoveryIssueKind = "engine_unavailable"
    RecoveryIssueExternalStateUnrecoverable   RecoveryIssueKind = "external_state_unrecoverable"
    RecoveryIssueTorrentMetadataUnrecoverable RecoveryIssueKind = "torrent_metadata_unrecoverable"
)

type RecoveryIssue struct {
    JobID string            `json:"jobId"`
    Kind  RecoveryIssueKind `json:"kind"`
}

type RecoverySummary struct {
    ReconciledFinalizations       int             `json:"reconciledFinalizations"`
    ReattachedTransfers           int             `json:"reattachedTransfers"`
    RestartedMetadataAcquisitions int             `json:"restartedMetadataAcquisitions"`
    InterruptedMediaJobs          int             `json:"interruptedMediaJobs"`
    Issues                        []RecoveryIssue `json:"issues,omitempty"`
}
```

### 7. Fields Removed and Data-Minimization Rationale

- **Removed `SanitizedContext`:** Free-form context strings represent an unnecessary secret-leak risk (e.g. leaking raw URLs, query tokens, filesystem paths, or backend error text). Removed entirely in favor of typed `Kind` values.
- **Removed `Engine`:** The current Job entity in SQLite and the StateSync stream already track engine identity. `RecoveryIssue` strictly communicates the intervention fact without duplicating current-state metadata.
- **Data Minimization:** `RecoveryIssue` contains strictly `jobId` and `kind`. Frontend wording is generated purely from the typed `Kind` mapping and aggregate counters. Zero regex redaction is required.

### 9. Distinguishing Discovered Engine State from Recovery Failure

- If GoDownloader queries an external engine (`aria2`, `qBittorrent`) and the engine returns `StatusFailed` (e.g. tracker error or disk full in qBittorrent), this is **discovered current state** from the daemon. It was not caused by GoDownloader restarting. The job is updated with the engine's error without adding an issue to `RecoverySummary`.
- Conversely, if GoDownloader marks a job `StatusFailed` because it cannot locate engine credentials, engine adapters, `.torrent` metadata files, or because an ephemeral child process was terminated by application exit, that **is** a startup recovery intervention and is faithfully recorded in `RecoverySummary`.

---

### 10. Engine & Torrent Taxonomy Decisions

- **`engine_unavailable`:** Reserved exclusively for branches where an engine adapter is literally unavailable in GoDownloader's engine registry (`m.engines.Get(...)` returns `!ok`).
- **`external_state_unrecoverable`:** Used when `EngineID` is missing, `eng.Status()` returns an error ("external engine state could not be recovered"), or the engine returns an unrecognized status. Accurately describes that the external transfer state could not be reconstructed without asserting unsupported daemon-internal failure modes.
- **`torrent_metadata_unrecoverable`:** Replaces the narrower `torrent_metainfo_missing`. Used when torrent hydration fails, metainfo records are missing, `.torrent` files are missing, or awaiting-selection metadata was lost.

### 11. Finalization Count Semantics

- **ReconciledFinalizations is incremented only after the durable FinalizationPhaseComplete journal update succeeds.**
- It increments strictly when a journal record that was pending at THIS startup (in phase `Prepared`, `InProgress`, `Validated`, `DBCommitted`, or `CleanupPending`) is successfully reconciled to `FinalizationPhaseComplete`.
- If the durable journal update to `FinalizationPhaseComplete` fails, `ReconciledFinalizations` is NOT incremented, `rec.Phase` is not set to `Complete`, and no false recovery fact is claimed (validated by `TestRecoverySummary_DurableCompleteUpdateFailure_NotCountedAsReconciled`).
- The exact documented meaning is: **"startup reconciliation completed remaining finalization work"**, not "the file was moved during this startup."
- A startup journal record already in `db_committed` or `cleanup_pending` still counts when startup completes its remaining cleanup and journal transition.
- It does NOT count historical journal entries that were already marked `Complete` or `Failed` before startup.

### 12. Single Reliable Summary-Freeze Path & Early-Return / Error Safety

- `recover()` utilizes a single reliable defer to freeze and store the accumulated summary:
  ```go
  var summary RecoverySummary
  defer func() {
      m.mu.Lock()
      m.recoverySummary = summary.Clone()
      m.mu.Unlock()
  }()
  ```
- This ensures EVERY return path from `recover()`—including when `ListRecoverable` fails with a repository error, when zero recoverable jobs exist, or on normal loop completion—publishes all recovery facts accumulated up to that point.
- The summary is strictly frozen under `m.mu.Lock()` before `recover()` returns to `ResourceGovernor` reconstruction and `Scheduler.Start()`.
- Validated by unit tests `TestRecoverySummary_EarlyReturnSafety_FinalizationPreserved` and `TestRecoverySummary_ListRecoverableError_FinalizationPreserved`.

### 12b. Reattached Transfers Counter Placement & Seeding Invariants

- Inspecting the `case StatusDownloading, StatusQueued, StatusSeeding:` branch proves counter placement correctness:
  ```go
  if j.Type == TypeTorrent && status.Status == StatusSeeding && !j.SeedAfterComplete {
      log.Printf("recovery: torrent job %s is seeding in engine but seedAfterComplete=false; completing and removing from daemon", j.ID)
      _ = m.finalizeCompletedTorrent(ctx, j)
      return
  }
  ```
- Because this path invokes `finalizeCompletedTorrent` and returns immediately, it NEVER reaches `m.addActive(j)` or `summary.ReattachedTransfers++`. Thus `ReattachedTransfers` remains `0`.
- For `seedAfterComplete == true` or active downloading, the job proceeds to `m.addActive(j)` and increments `summary.ReattachedTransfers++` (1).
- Proved by exact unit tests:

  - `TestRecoverySummary_Seeding_SeedAfterCompleteTrue_CountedAsReattached`

### 13. Summary Freeze Timing

- The recovery summary is populated synchronously inside `StartBackgroundTasks(ctx)`.
- It is deep-copied and stored on `m.recoverySummary` before `m.resourceGovernor.ReconstructJob(j)` and `m.scheduler.Start(ctx)` are called.
- After the scheduler starts, the recovery summary is completely immutable. Runtime job events do not mutate it.

### 15. RecoveryBanner Finalization Wording & Deduplication

- Finalization wording is precise and avoids vague completion claims:
