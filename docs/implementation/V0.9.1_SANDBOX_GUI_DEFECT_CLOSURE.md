## 1. Original Sandbox findings (GUI)

Source: the Windows Sandbox acceptance report, kept outside the repository and **not modified**. Candidate: `45a123f`, exe `2c45bf45…`.

Session 1 (offline, S1–S13): 13/13 executed, all functional checks passed. Two defects:
- **D-1 (release blocker).** Launching the installed app opens a second **console window** next to the GUI, streaming internal logs.
  - Closing that console terminates the process outside the controlled Quit sequence.
  - Close-to-tray (S7) hid the main window but left the console on the taskbar.
- **D-2 (cosmetic).** Settings → Dependencies → "What works right now" read: "Unavailable until yt-dlp and FFmpeg and FFprobe is ready."

## 2. Root cause of D-1 (SRC, PE)

**Executable header:**
- The candidate `GoDownloader.exe` has PE optional-header `Subsystem = 3` (`IMAGE_SUBSYSTEM_WINDOWS_CUI`, console).
- Windows gives every console-subsystem program a console window at launch.
- The superseded `e894253` candidate is also subsystem 3, so the defect is pre-existing, not a regression.

**Build configuration:**
- `build/windows/Taskfile.yml` production `BUILD_FLAGS` linked with `-ldflags="-w -s -X …buildinfo…"` and **no `-H windowsgui`**.
- The Wails v3 viability spike (`docs/implementation/SPK-SYN3-01_WAILS_V3_VIABILITY.md`) built with `-ldflags="-w -s -H windowsgui"` and recorded "Subsystem: Windows GUI", but the product Taskfile never carried the flag.

**No guard existed:** no test or CI step checked the subsystem.

**Second, latent half of D-1:**
- The same spike (risk 3) required `ProcessSupervisor` to "continue to enforce `CREATE_NO_WINDOW`". **It never did.** `internal/process/tree_windows.go` only added `CREATE_SUSPENDED`, and the tool probes set no flags.
- Under the console subsystem this was invisible, because yt-dlp, FFmpeg, FFprobe and Deno shared GoDownloader's own console.
- With the GUI subsystem alone, **every** analysis, download and version probe would have opened its own console window.
- The linker flag is therefore only half the fix.

## 3. Exact changes

### Linker configuration

`build/windows/Taskfile.yml`, production (non-DEV) branch only:

```diff
-…{{else}}-tags production -buildvcs=false {{.GO_TRIMPATH}} -ldflags="-w -s -X downloader/internal/buildinfo.Version=0.9.1 …
+…{{else}}-tags production -buildvcs=false {{.GO_TRIMPATH}} -ldflags="-w -s -H windowsgui -X downloader/internal/buildinfo.Version=0.9.1 …
```

**Preserved:**
- `-w -s`;
- Version, Commit and Modified (dirty) injection;
- `Configuration=production`;
- `-tags production`, `-buildvcs=false`;
- opt-in `{{.GO_TRIMPATH}}`.

**Unchanged:** the DEV branch, `cmd/server`, Wails architecture and the single executable. No launcher was added.

### Child-process consoles

- **New:** `internal/process/console_windows.go` (`HideConsoleWindow`: ORs `CREATE_NO_WINDOW` into `SysProcAttr.CreationFlags`, preserving existing flags) and `console_other.go` (no-op off Windows).
- **`internal/process/tree_windows.go` `setup`:** keeps `CREATE_SUSPENDED` and adds `HideConsoleWindow(cmd)`. This covers every supervised (owned) process.
- **`internal/toolmanager/manager.go` `probeVersionTimeout`:** calls `process.HideConsoleWindow(cmd)`. This covers every version and dependency probe, including managed yt-dlp verification.

### Candidate gate

`build/windows/write-build-manifest.ps1`:
- New `Get-PESubsystem`, a bounded PE-header reader.
- The manifest refuses (exits non-zero, writes nothing) unless the desktop executable is a well-formed PE image with subsystem 2.
- This check runs **before** the executable is ever started, ahead of the existing marker check and `--print-build-info` probe.

### D-2

`internal/toolmanager/media_dependencies.go` `missingRequirements` (see Section 8).

### CI

`.github/workflows/ci.yml`: the packaging-test inventory now also requires the four new PE tests (11 in total) to execute and pass.

## 6. Build-info and manifest compatibility (SRC, BUILD, RUN)

**Code path (SRC):**
- `--print-build-info` is the first thing `main()` handles (`cmd/desktop/main.go`).
- It marshals `buildinfo.Current()`, prints, and returns before WebView2 detection, data-root resolution, core start, database, single-instance or tray setup.

**Real build (BUILD):**
- The isolated packaging run (exit 0) wrote the manifest through the unchanged probe (`System.Diagnostics.Process`, redirected stdout, 15 s timeout).
- Manifest values: `embeddedCommitMatchesHead: true`; embedded `commit 45a123f…-dirty`, `dirty: true`, `configuration: production`, `platform: windows/amd64`.
- `releaseCandidate: false` is **correct and truthful**: the clone carried this uncommitted change.

**Direct run of the new executable (RUN):**
- Identity verified first: SHA-256 `3b1fe781…` = manifest, PE subsystem 2.
- Run with `APPDATA`, `LOCALAPPDATA`, `USERPROFILE`, `TEMP` and `TMP` all pointing to empty scratch folders.
- Results: exit 0 in 130 ms, empty stderr, valid JSON (version 0.9.1, commit `45a123f…-dirty`, dirty true, production, windows/amd64, injected).
- **0 files created** in the disposable environment, so no database and no data root. No GoDownloader process before or after. The process exited at once, so no window or tray icon was created.

**Interactive use (known behaviour of GUI-subsystem programs):**
- Typing `GoDownloader.exe --print-build-info` in a console **without redirection** shows nothing, because the program has no console.
- Redirected or piped use works, and that is how the manifest uses it: for example `> file`, `| more`, or PowerShell `& .\GoDownloader.exe --print-build-info | Out-String`.
- The same applies to the other diagnostic flags (`--print-data-root`, `--diagnostic-smoke`, `--print-*-status`).
- No CLI change was needed for provenance verification; none was made.

## 7. External-process regression assessment (SRC, TEST)

| Path | Launch mechanism | Console handling now | Ownership / termination |
|---|---|---|---|
| yt-dlp analysis (`internal/engine/ytdlp/analyzer.go`) | `Supervisor.StartOwned` | `CREATE_SUSPENDED` + `CREATE_NO_WINDOW` | Job Object (unchanged) |
| yt-dlp download (`ytdlp.go`); FFmpeg is started **by** yt-dlp | `Supervisor.StartOwned` | yt-dlp: hidden console; FFmpeg inherits it, so no window | Job Object includes descendants (unchanged) |
| Version and dependency probes: yt-dlp, FFmpeg, FFprobe, Deno; managed yt-dlp staging and verification | `probeVersionTimeout` | `CREATE_NO_WINDOW` | Context timeout + 1 s `WaitDelay` (unchanged) |
| aria2 / qBittorrent | HTTP RPC/WebUI to external daemons; **no process is started** | n/a | External daemons are never started, stopped or signalled |
| "Open folder" | `explorer` (GUI program) | n/a | Not owned |

**Why `CREATE_NO_WINDOW`:**
- `DETACHED_PROCESS` would leave the child with no console at all, so each console grandchild (FFmpeg) would open its own window.
- With `CREATE_NO_WINDOW` the child has a hidden console that its children inherit. `TestStartOwned_ChildRunsWithHiddenConsole` asserts the child has a console.

**Preserved:**
- Suspension, Job Object assignment and verification, resume, `terminateJobAndWait` membership checks and cancellation were not touched.
- Existing process-tree, cancellation and supervisor tests all pass, including under `-race`.
- No unrelated process is enumerated or terminated.

**Logging note (unchanged behaviour, now visible):**
- The desktop logs only to stderr; there is no log file. Under the console subsystem those lines appeared in the D-1 console window.
- Under the GUI subsystem they are not displayed anywhere unless stderr is redirected; runtime panics behave the same.
- Adding a log file is out of scope for this correction. It is recorded as a diagnostics follow-up for owner prioritisation.
