## 4. Cryptographic trust root

```text
Pinned public key (embedded in source, go:embed)
    -> SHA2-256SUMS + SHA2-256SUMS.sig (official asset API, bounded)
    -> detached OpenPGP signature verified (signer fingerprint, digest, and algorithm enforced)
    -> strict manifest parse -> exact yt-dlp.exe digest
    -> stream yt-dlp.exe into managed-store staging (SHA-256 while streaming)
    -> digest verified (stream hash AND re-hash from disk)
    -> only now: bounded --version probe (output must equal the release tag)
    -> immutable content-addressed promotion (re-hashed)
    -> exclusive UsageGate -> ledger revalidation -> transactional activation
```

- There is no trust-on-first-use, no network key fetch, and no automatic rotation. If the embedded key does not match the pinned fingerprint, `newTrustRoot` fails closed with `ErrUntrustedSigningKey`.
- Verifier hardening: `MinRSABits: 3072`. MD5, SHA-1, RIPEMD-160, and SHA-224 are rejected (go-crypto config). An explicit allowlist then requires a SHA-256/384/512 digest and an RSA or EdDSA/Ed25519/Ed448 key. Armored signatures are refused (upstream ships binary). Manifest and signature are bounded at 64 KiB each.
- An unsigned checksum file is never trusted.

## 8. Stable release discovery

- The fixed endpoint is `/repos/yt-dlp/yt-dlp/releases/latest`. Draft or prerelease responses are refused. The tag must parse as a stable `YYYY.MM.DD[.patch]` version.
- Each of `yt-dlp.exe`, `SHA2-256SUMS`, and `SHA2-256SUMS.sig` must appear **exactly once** by exact name. Their numeric IDs and declared sizes are bounded. Metadata selects asset IDs only; it is never treated as proof of authenticity.
- Version policy: a newer release proceeds; the same release with a valid active binary is a no-op; an older release is refused with `DOWNGRADE_REFUSED`. The candidate's `--version` output must equal the tag component-wise.
- **Replay caveat (documented):** a validly signed *old* release could be served by an attacker who controls the network path. Anti-downgrade prevents replacing a newer managed install. A **first** install, however, relies on release discovery (TLS to `api.github.com`) for freshness. The detached signature authenticates *content*, not that a release is "latest".

## 9. Network / redirect policy

- HTTPS only. Exact host allowlist: `api.github.com` and `release-assets.githubusercontent.com`. There is no `*.githubusercontent.com` wildcard.
- **Observed live:** the asset API answered `302 -> https://release-assets.githubusercontent.com/...`, then `200`, for all three assets (one hop). The allowlist needed no change.
- At most **3** redirect hops. Every hop is re-checked for scheme and host. `Authorization`, `Cookie`, and `Proxy-Authorization` are stripped on redirect. Requests are unauthenticated: no GitHub token is ever configured.
- Asset URLs are always built as `/repos/yt-dlp/yt-dlp/releases/assets/{numeric id}` with `Accept: application/octet-stream`. Metadata URLs are never followed.
- **Redirect privacy:** transport errors pass through `sanitizeNetError`, which drops the URL (and therefore any signed query) and keeps only a category and host. `TestAcquisition_LogsNeverContainSignedCDNTokens` captures logs and errors across success and failure paths and asserts that the fake CDN token never appears. Raw responses are never persisted.

Context cancellation is honoured. There are no retries. Truncated bodies (fewer bytes than declared) and oversized bodies fail.

## 11. Signed-manifest parsing

`parseSHA256Manifest` operates only on an already authenticated manifest. Every line must match `^<64 hex> [ *]<bare name>$`; any malformed line rejects the whole manifest. It also rejects binary content, `..`, path separators, oversized input, a missing asset, and duplicate entries. Matching is exact: `yt-dlp.exe.zip`, `yt-dlp_x86.exe`, and `yt-dlp` never match `yt-dlp.exe`.

## 12. Hash-before-execution proof

- Execution happens in exactly two places, and both run only after a digest check: the candidate probe in `stageAndVerify`, after the stream hash and an on-disk re-hash both equal the authenticated digest; and startup verification in `verifyManagedRecord`, after the stored file's hash equals the ledger digest.
- The test harness hashes every file **at the instant it would execute** and fails on any unauthenticated content (`assertOnlyAuthenticatedExecuted`).
- **Mutation proof:** with both digest checks disabled, `TestAcquisition_HashMismatchNeverExecutes` failed because the tampered binary was actually probed. The source was restored byte-identical (hash verified).

## 13. Content-addressed storage layout

```text
<dataDir>/bin/yt-dlp/<sha256>.exe        immutable, selected only via the ledger
<dataDir>/bin/yt-dlp/.partial-<rand>.exe staging (same filesystem), removed on failure
<dataDir>/bin/yt-dlp/.quarantine-…       a pre-existing corrupt file moved aside (never overwritten in place)
<dataDir>/bin/yt-dlp.exe                 legacy location — recognised, never touched (Section 14)
```

- An existing `<sha>.exe` is **re-hashed** before reuse. If its content is wrong it is moved aside, never rewritten in place.
- `ensureRoot` refuses to use `bin` or `bin/yt-dlp` if either is a symlink, junction, or other reparse point (`ModeSymlink|ModeIrregular`). The test creates a real NTFS junction and asserts refusal.
- Ledger file names must be the exact content address of their own digest, so traversal and absolute paths are rejected.
- Durability: the staged file is `Sync`ed before close, then renamed. On Windows a directory cannot be fsynced through `os.File`; NTFS journals the rename. This is the practical Windows extent, **not** a cross-filesystem power-loss atomicity guarantee.
- **Garbage collection** *(corrected by the acceptance gate, finding A-1)*. It deletes only files whose ownership and obsolescence are provable:
  - content-addressed binaries that **this** ledger itself recorded and later retired or quarantined;
  - `.partial-*` staging files, only while holding the cross-process acquisition ownership lock. *(Part III: originally age-based (24 h); age alone is not proof of abandonment.)*
  - `.quarantine-*` files older than 7 days, also only while holding the ownership lock.

  Content-addressed files unknown to this ledger are **kept**, because another database sharing the data directory may own them. Orphaned verified candidates are reused, after re-hashing, by the next install of the same release. GC refuses to run if the store root is a link or junction, and runs only at startup or under the acquisition lock. Deletion failures are reported as deferred: a test runs a real executable copy and confirms that Windows refuses the delete and GC defers it.
- **Design change, deliberate:** this replaces the historical single managed path and the previously proposed rename rotation. No activation journal was introduced. Binaries are immutable and the SQLite row is the only pointer, so the only crash windows are an orphaned verified file (harmless; removed at startup) or an uncommitted transaction (rolled back).

## 14. Legacy path compatibility

`<dataDir>/bin/yt-dlp.exe` is still resolved, after the authenticated ledger. Its provenance is now `managed_legacy` (formerly `managed`) and its verification stays `version_probed`. It is never hashed into authority, moved, overwritten, or deleted (`TestRecovery_LegacyPathPreservedAndNeverAuthenticated`). This is the one intentional observable change to existing resolution output.

## 15. SQLite schema / writer changes

**Design choice:** a separate, additive `managed_tool_ledger` table rather than migrating the `tool_records` primary key. Rebuilding a PK is the destructive option. A separate table makes it *physically impossible* for an external observation to overwrite managed authority.

```sql
managed_tool_ledger(name, sha256, version, release_tag, file_name, signer_fingerprint, status,
                    authenticated_at, created_at, updated_at,
                    PRIMARY KEY(name, sha256), CHECK(length(sha256)=64),
                    CHECK(status IN ('active','last_known_good','retired','quarantined')))
UNIQUE INDEX ... (name) WHERE status='active'
UNIQUE INDEX ... (name) WHERE status='last_known_good'
```

- **Migration `migrateToV091ManagedTools`:** runs in one transaction with an `app_settings` marker, so it is idempotent. It takes a `VACUUM INTO <db>.pre-v091.bak` backup first, using the same convention as V0.8. It creates the ledger and indexes. Duplicate `active` rows in `tool_records` are normalised deterministically: the newest `updated_at`, ties broken by version, stays active and the others become `deprecated`. No row is deleted, and **no legacy row is ever copied into the managed ledger**. A failure rolls back fully.
- **`SaveToolRecord`:** now transactional. It refuses `verification_status = 'authenticated_release'`, so authenticity cannot be forged, and a new active observation supersedes other active rows of the same tool, so there is at most one active observation.
- **ToolManager `recordTool`:** never writes authenticated releases to `tool_records`.

## 16. One-active invariant

The database itself enforces at most one active and at most one LKG row per tool through partial unique indexes; a test inserts directly and is rejected. Exactly one active row exists after a successful activation. History is bounded: retired and quarantined rows beyond 3 are pruned inside the activation transaction.

## 17. Transactional activation

`CommitToolActivation(ctx, newActive, previousActive)` runs as one SQLite transaction that takes the write lock first. It verifies that the stored active row equals `previousActive` (or that none exists), retires the old LKG, demotes the previous active row to LKG, upserts the new row as active, and prunes history. Any mismatch returns `ErrManagedLedgerConflict` with no change. Failures propagate. An injected trigger failure after the demotion rolls the whole transaction back (`TestManagedLedger_RollbackOnInjectedFailure`). It is never assembled from multiple independent `SaveToolRecord` calls, and real column names (`name`, `status`, …) are used.

## 19. LKG restoration

LKG restoration happens only on **integrity** failures: a missing file, a hash mismatch, a non-content-addressed name, a signer that is not the active trust root, or a version mismatch. If the LKG passes the same verification, `RestoreLastKnownGood` atomically quarantines the failed active row and promotes the LKG, with expected-state checks. A safe diagnostic is exposed ("…restored the previous authenticated version …"). Transient start failures never rewrite the ledger.

## 20. Startup authenticated resolution

The precedence is: authenticated ledger → legacy managed path → configured → PATH. For the ledger, startup reads the unique active row, checks that the path is in the store, hashes the file, and only then runs a bounded probe (20 s, because PyInstaller self-extraction is slower than the 3 s generic probe). It requires version agreement and returns `authenticated_release` / `managed_release`. A version probe never downgrades an authenticated release, and generic observations cannot overwrite the ledger. `ToolInfo.Available()` accepts both `version_probed` and `authenticated_release`.

## 21. UsageGate integration

- No second lock was added. `App.New` passes the Checkpoint 1 engine (whose `UsageGate` is shared by analyses and downloads) to `ToolManager.SetUsageCoordinator`.
- Download and verification happen **before** the gate is involved. Activation then calls `TryExclusive` (refused with `TOOL_IN_USE` while any analysis or download holds shared use), re-reads the ledger to reject stale decisions, and re-hashes the promoted file before the short commit.
- Any failure reopens the gate. Jobs are never killed.
- Real-engine tests cover refusal during analysis and during download, no new execution after activation, already-current not blocking, and a failed activation reopening the real gate.

## 22. Restart-required enforcement

- **Policy (Beta):** after a successful activation the gate **stays exclusive** until backend restart, and `restartRequired=true`.
- Running processes are untouched. New `AcquireUse` calls are refused, so the live process never switches binaries.
- `Engine.MaintenancePending()` lets `CreateWithOptions` and `SelectFormat` return the typed `YT_DLP_RESTART_REQUIRED` (HTTP 409) up front, with no job persisted.
- Already-current results do not close the gate.
- The registry is never mutated at runtime. A first install registers the engine only on restart.
- *(Corrected by the acceptance gate, finding A-2.)* Until restart, the scheduler leaves media jobs queued, `dispatchQueuedJob` returns a no-state-change signal as a race backstop, and analyses refused by the gate stay `ANALYZING` for recovery. No job is failed because of a successful tool update.

## 23. Service and transport integration

- **Core operations:** `YtdlpStatus`, `InstallYtdlp`, `UpdateYtdlp`, `CheckYtdlpUpdate`. Results are `AcquisitionResult` / `UpdateCheckResult` / `ManagedToolStatus`, all path- and URL-free.
- **Typed codes:** `UNSUPPORTED_PLATFORM`, `TOOL_IN_USE`, `NETWORK_FAILURE`, `INVALID_SIGNATURE`, `HASH_MISMATCH`, `UNTRUSTED_SIGNING_KEY`, `INVALID_RELEASE`, `DOWNGRADE_REFUSED`, `ACTIVATION_FAILED`, `RESTART_REQUIRED`, `ACQUISITION_IN_PROGRESS`. Each has a fixed, safe message.
- **Desktop:** native Wails service methods (`GetYtdlpToolStatus`, `InstallYtdlp`, `UpdateYtdlp`, `CheckYtdlpUpdate`) with no parameters and no localhost transport. Bindings were regenerated.
- **HTTP:** `GET /api/v1/tools/yt-dlp` and `POST …/install|update|check-update` sit under the existing `SecurityMiddleware` and Host validation. Tests prove that no-session and no-CSRF requests are refused, that request bodies (for example an injected URL or hash) are ignored, and that responses contain no paths, URLs, or internal error detail.

## 25. JavaScript-runtime diagnostics

- **Audit:** GoDownloader never passes `--remote-components`, so no EJS components are fetched remotely. Analysis uses `--no-warnings`.
- **Upstream statement (README, verified):** full YouTube support needs `yt-dlp-ejs` plus a JavaScript runtime (Deno recommended and enabled by default; Node.js, Bun, QuickJS supported).
- **Change:** `withJSRuntimeHint` appends an actionable hint when yt-dlp output mentions a JavaScript runtime, challenge-solving failure, signature-solving failure, `yt-dlp-ejs`, or `--remote-components`. Download failures evaluate the whole stderr.
- GoDownloader installs or bundles no runtime and does not claim that yt-dlp alone guarantees YouTube downloads.

## 26. FFmpeg ownership preservation

FFmpeg resolution, ownership (`external_user`), and its `--ffmpeg-location` wiring are unchanged. Acquisition never touches FFmpeg, and configured or PATH executables are never modified (`TestRecovery_ExternalConfiguredBinaryUntouchedByInstall`).

## 27. Security / privacy review

- Nothing executes before an authenticated digest match (Section 12).
- The trust root is pinned, the signer and algorithms are enforced, and failures are closed.
- Network: exact host allowlist, HTTPS only, bounded hops, credential headers stripped, no tokens configured, signed CDN queries never logged or returned.
- Filesystem: writes are confined to a reparse-checked store, files are content-addressed and immutable, and unknown or legacy or user files are never deleted.
- Ledger authority is isolated from observations; authenticity cannot be forged through `SaveToolRecord`.
- Public DTOs and messages carry no executable paths, CDN URLs, headers, or cookie data. The support bundle remains path-free.
- **Residual same-user TOCTOU:** a process running as the same Windows user can replace a store file between hash and execution. That attacker can already replace any per-user executable, so this is outside the threat model and is documented in Section 32.

# Part III — Final Safety Checks Before the Git Checkpoint

The baseline was unchanged: HEAD = origin/dev = `e0c0047`, main = origin/main = `7c354db`, and `.gitignore` byte-identical. The Part II independence caveat still applies: these checks were run by the implementing agent.

## S-A. Cross-process temporary-file ownership — gap found and closed

**Finding.** Part II cleanup (A-1) deleted `.partial-*` files older than 24 h on **age alone**. Age is not proof of abandonment: a stalled writer, a suspended machine, or a system-clock jump can make a live candidate look old. Another process sharing the data directory (with a different database) could then delete a staging file that a live acquisition still owns.

**Fix: ownership is established, not inferred.**

- A store-wide exclusive OS lock, `<dataDir>/bin/yt-dlp/acquisition.runtime.lock`, reuses the existing `runtimeguard` primitive: an exclusive `CreateFile` share mode on Windows, `flock LOCK_EX|LOCK_NB` on Unix. The OS releases it when the process exits.
- Every acquisition takes it **before** any staging file exists and holds it until promotion, activation, and its own cleanup finish. A second acquisition in any process gets `ACQUISITION_IN_PROGRESS`.
- Startup cleanup removes staging and quarantine files **only while holding that lock**. Holding it proves no live acquisition exists in any process, so leftover partials are crash remnants and are removed regardless of age. If another process holds the lock, all ambiguous scratch files are kept.

**Unchanged guarantees:**

- Active and LKG binaries are never removed.
- Content-addressed binaries unknown to this ledger are never removed, so the `--diagnostic-smoke` database cannot delete the main application's binaries (`TestAcquisition_CleanupNeverDeletesAnotherLedgersBinaries`).
- Unknown names, including the lock file, are never touched.
- Cleanup and promotion refuse a junctioned or linked store root (`TestStore_GarbageCollectionRefusesJunctionedRoot`).

**Regression test.** `TestAcquisition_CleanupNeverDeletesAnotherProcessesLiveStaging` holds the real OS lock to stand in for another process's live acquisition. A 72-hour-old partial is **kept** and a concurrent acquisition is refused. After the lock is released, the abandoned partial is removed. **Mutation proof:** forcing cleanup to ignore lock ownership makes this test fail. `TestStore_GarbageCollectionScope` now also asserts that very old scratch files are kept without ownership.

**Follow-up found by the repository-write check.** The first version of this fix made startup cleanup take the lock unconditionally, which *created* `bin/yt-dlp/` and its lock file even when no managed store existed. The full-suite snapshot caught the desktop tests leaving `cmd/desktop/data/bin/yt-dlp/acquisition.runtime.lock` in the repository tree. Startup cleanup now returns immediately when the store does not exist, so it creates nothing. The single artifact created by that validation run (the lock file and its new directory, both timestamped during the run) was removed; the pre-existing `cmd/desktop/data/bin` directory was untouched. Regression test: `TestAcquisition_StartupCleanupCreatesNothingWithoutStore` (mutation-proven).

**Residual (documented):** two *different* ledgers that both select the same content-addressed binary share one file. If one ledger retires it, its cleanup can remove a file the other ledger still selects. The other ledger then detects the missing file by hash at startup and restores its LKG or reports truthfully. This requires two different databases to perform overlapping installs in one shared data directory, which is an unsupported configuration. Neither the diagnostic smoke mode nor normal operation installs from a second database.

## S-B. Installation endpoint authorization — gap found and closed

**Verified boundaries:**

- The HTTP server refuses non-loopback binds unconditionally (`CheckNonLoopbackBind` in `cmd/server/main.go`, before `ListenAndServe`), so remote network clients cannot reach any route, even with `DISABLE_AUTH=1`.
- In normal mode, every tool route sits behind Host validation, Origin/Referer validation, session cookie, and CSRF token.
- Wails uses native, parameterless service bindings with no localhost server.

**Finding.** The A-7 guard enforced Origin/Referer even under `DISABLE_AUTH`, but explicitly *allowed* requests without those headers. Origin checking is not authentication. With auth disabled, any local process on the loopback interface (including another OS user's process) could trigger an executable download and activation.

**Fix.** `SecurityManager.RequireAuthenticatedSensitiveAction` (replacing `RequireAllowedOrigin`) wraps the install, update, and check-update routes:

- While authentication is disabled, they return **403 `AUTH_REQUIRED`** for every caller.
- Otherwise the full session and CSRF middleware has already authenticated the request, and the origin is checked again.
- Read-only status stays available. Developers who need installs use normal authenticated mode.

**Regression test.** `TestToolsAPI_InstallRefusedWhenAuthDisabled` asserts the following, and **mutation proof:** removing the `DISABLE_AUTH` refusal makes it fail.

- Cross-origin (Origin or Referer) **and** header-less local requests to all three mutation routes are refused, and the install service is never invoked.
- The status route stays available.
