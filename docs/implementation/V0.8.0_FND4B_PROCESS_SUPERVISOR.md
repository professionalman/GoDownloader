## 1. Executive Summary

FND-4B delivers the **ProcessSupervisor** capability for GoDownloader under strict **Ponytail / YAGNI** principles. It establishes kernel-level process-tree ownership over child and descendant processes on Windows using native Win32 **Job Objects** (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`), eliminating orphaned process leaks (`yt-dlp`, `ffmpeg`) during job cancellation, failure, context cancellation, or application shutdown/crash.

It also enforces the vital safety invariant that external user-owned daemons (`qBittorrent`, `aria2`) and shell launchers (`explorer`, `open`, `xdg-open`) are **never** process-supervised, enumerated, or terminated.

## 4. Current Cancellation Weaknesses & Fix

### Weakness in Previous Implementation
1. **Orphaned Descendants on Windows:**  
   Go's standard library `exec.CommandContext(ctx, ...)` on Windows calls `cmd.Process.Kill()` when `ctx` is done. On Windows, `Process.Kill()` only kills the immediate root child (`yt-dlp.exe`). Any child processes spawned by yt-dlp (e.g., `ffmpeg.exe` post-processing or muxing streams) are left running in the background indefinitely, consuming CPU and locking output files.
2. **Abrupt Crash Orphanage:**  
   If GoDownloader crashes or is abruptly killed, standard child processes continue running as orphans.
3. **Context / Kill Race:**  
   Simultaneously invoking `cmd.Process.Kill()` and external cleanup races against process exit.

### The FND-4B Fix
- Long-running tool processes are wrapped in `internal/process.Supervisor`.
- On Windows, each managed process tree is assigned to a dedicated Win32 **Job Object** configured with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`.
- `cmd.Cancel` is explicitly bound to tree termination (`proc.Terminate()`), ensuring context cancellation terminates the entire process tree without racing against standard library `Process.Kill()`.

---

## 5. Ponytail / YAGNI Decisions

1. **No ProcessFactory / Strategy Hierarchy:**  
   A single concrete `Supervisor` struct and a simple `ManagedProcess` handle provide all necessary capabilities.
2. **No Second Job State Machine:**  
   The `ProcessSupervisor` owns **process lifetime**. `job.Manager` remains solely authoritative for **job state**.
3. **No Process Persistence Theater:**  
   Operating system PIDs and Job Object handles are runtime-only and are **never** persisted to SQLite `job_executions` or `tool_records`.
4. **No Global Process Enumeration / Killing:**  
   Zero usage of `taskkill /IM`, `pkill`, or process scanning by executable name. Ownership derives strictly from handles created by GoDownloader.
5. **No Third-Party Process Management Dependencies:**  
   Implemented entirely using existing `golang.org/x/sys/windows` and Go standard library.

## 6. ProcessSupervisor Boundary & API

Located in package `downloader/internal/process`:

```go
type ProcessSpec struct {
    ID      string // Unique identifier (e.g. Job ID)
    JobID   string // Associated Job ID if applicable
    Tool    string // Tool name ("yt-dlp", etc.)
    Purpose string // Purpose ("download", etc.)
}

type ISupervisor interface {
    StartOwned(ctx context.Context, cmd *exec.Cmd, spec ProcessSpec) (*ManagedProcess, error)
    Terminate(id string) error
    TerminateAll() error
    Shutdown(ctx context.Context) error
    Get(id string) *ProcessInfo
    ActiveCount() int
    List() []*ProcessInfo
}
```

### `ManagedProcess`
- `PID() int`: Returns the root process PID.
- `State() ProcessState`: `StateRunning`, `StateExited`, or `StateTerminated`.
- `WasTerminated() bool`: Reports whether termination was requested.
- `Terminate() error`: Idempotent process-tree termination.
- `Wait() error`: Memoized, thread-safe wait that reaps OS resources and unregisters the process from the supervisor registry.

## 7. Windows Job Object Design

Implemented in `internal/process/tree_windows.go`:

1. **Creation:** `windows.CreateJobObject(nil, nil)` creates an anonymous job object.
2. **Configuration:** Sets `windows.JobObjectExtendedLimitInformation` with `LimitFlags = windows.JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`.
3. **Attachment:** Immediately after `cmd.Start()`, opens the process handle with `windows.PROCESS_SET_QUOTA | windows.PROCESS_TERMINATE` and assigns it via `windows.AssignProcessToJobObject`.
4. **Kernel-Enforced Inheritance:** Any child process spawned by the root process (such as `ffmpeg` spawned by `yt-dlp`) automatically inherits the Job Object.
5. **Tree Termination:** `windows.TerminateJobObject(jobHandle, 1)` unconditionally terminates all processes currently assigned to the job object.
6. **Kill-On-Job-Close:** If GoDownloader terminates abruptly (or the handle is closed), the Windows kernel automatically terminates all processes in the job object.

---

## 8. Assignment Order & Race Decision

- **Analysis:** Between `cmd.Start()` (Win32 `CreateProcess`) and `windows.AssignProcessToJobObject`, there is a sub-millisecond window before the process is assigned.
- **Decision:** Starting processes suspended via `CREATE_SUSPENDED` would require undocumented `NtResumeProcess` or thread enumeration because Go's `exec.Cmd` does not expose the main thread handle (`hThread`). For `yt-dlp`, startup requires tens of milliseconds to parse Python bytecode and command-line arguments before any network connection or child spawn occurs. Therefore, immediate post-Start assignment is completely sufficient.
- **Fail-Closed Guarantee:** If `AssignProcessToJobObject` fails (e.g. access denied or process exited prematurely), `StartOwned` immediately calls `cmd.Process.Kill()`, closes the tree handle, and returns an explicit error (`ErrProcessTreeAttach`). An unassigned child is never left running.

## 9. Nested Job Objects Behavior

On Windows 8, Windows 10, Windows 11, and Windows Server 2012+, nested Job Objects are supported natively. If GoDownloader runs under a host Job Object (such as in CI, terminal hosts, or IDEs), child Job Objects nest cleanly. If assignment is restricted by an ancestor environment, `StartOwned` returns an explicit `ErrProcessTreeAttach` error and kills the child rather than proceeding unsupervised.

## 11. Wait Ownership & Concurrency Semantics

- **Single Wait Owner:** `ManagedProcess.Wait()` wraps `cmd.Wait()` with `sync.Once`. Subsequent or concurrent calls return the memoized exit error.
- **Stdout/Stderr Pipe Safety:** In `ytdlp.Engine`, output reader goroutines wait on `wg.Wait()` before `proc.Wait()` is called, preventing pipe read starvation.
- **Concurrency & Idempotency:**
  - `Terminate()` uses `termOnce.Do` and is completely safe to call repeatedly or concurrently with `Wait()`.
  - Supervisor registry operations (`StartOwned`, `Terminate`, `TerminateAll`, `Shutdown`, `Get`, `List`) are protected by a `sync.RWMutex`.

## 12. Shutdown Ordering

In `cmd/server/main.go`, shutdown follows the strict sequence:
1. Signal received (`SIGINT`/`SIGTERM`) -> `cancel()` cancels application context.
2. `server.Close()` terminates the HTTP server and stops accepting incoming requests.
3. `manager.Stop()` stops scheduler dispatch, cancels active job contexts, and calls `ytdlpEng.Shutdown()`.
4. `processSupervisor.Shutdown(timeoutCtx)` forcefully terminates all owned process trees and boundedly waits (up to 5s) for all processes to be reaped.
5. `db.Close()` closes SQLite database connections.

## 18. Final Atomic Windows Containment Verification

### 18.1 Trace of Windows Process Execution Path
The supervised Windows execution flow proceeds through five deterministic, ordered phases:
1. **Pre-Start Setup (`windowsProcessTree.setup`):**  
   Configures `cmd.SysProcAttr.CreationFlags |= windows.CREATE_SUSPENDED`.
2. **Suspended Process Creation (`cmd.Start()`):**  
   Invokes Go runtime process creation via `windows.CreateProcess`. The OS kernel allocates the process object, initializes address space, and creates the primary thread with a suspend count of 1.  
   **Crucial invariant:** At this point, the process has executed **zero instructions** of user or application code. It cannot spawn children or allocate external resources.
3. **Job Object Association (`windowsProcessTree.attach`):**  
   Opens a handle to the suspended process (`PROCESS_SET_QUOTA | PROCESS_TERMINATE | PROCESS_QUERY_INFORMATION`) and calls `windows.AssignProcessToJobObject(jobHandle, hProc)`.
4. **Containment Verification (`isProcessInJob`):**  
   Calls Win32 `IsProcessInJob(hProcess, jobHandle)` to cryptographically and kernel-level confirm that the process is an active member of the target Job Object.
5. **Thread Resumption (`resumeProcess`):**  
   Takes a thread snapshot via `windows.CreateToolhelp32Snapshot(TH32CS_SNAPTHREAD, 0)`, locates the primary thread of the target PID, opens it with `THREAD_SUSPEND_RESUME`, and invokes `windows.ResumeThread`. The process transitions to active execution **already fully contained inside the Job Object**.

### 18.2 Confronting the Atomic Assignment Question
Can a Windows child process be started directly inside a Job Object without an uncontained execution window? Three options were rigorously evaluated:

- **Option A: Pre-creation assignment via `PROC_THREAD_ATTRIBUTE_JOB_LIST` (`0x2000D`):**  
  *Analysis:* Supported natively on Windows 10 (1703+) and Windows Server 2016+. However, Go's standard library `syscall.SysProcAttr` does not expose arbitrary attribute lists or `JobList`. Bypassing `exec.Cmd.Start()` to call `CreateProcessW` directly breaks Go's internal stdio pipe plumbing (`cmd.closeAfterStart`, `cmd.closeAfterWait`, copier goroutines), leading to deadlocks on stdout scanners or requiring hundreds of lines of fragile runtime-mirroring code.
- **Option B: Suspended Creation + Job Assignment + Resume (`CREATE_SUSPENDED`):**  
  *Analysis:* Supported natively by Go's `cmd.SysProcAttr.CreationFlags` on all Windows versions. Provides **true atomic execution containment**: because the process is created suspended, the time window between process creation and Job Object assignment contains **zero opcodes of executed code**. The child process cannot spawn any grandchildren or execute adversarial logic before it is safely inside the Job Object. It preserves 100% of Go's standard library `exec.Cmd` piping, scanner compatibility, and `Wait()` semantics.
- **Option C: Post-start immediate assignment without suspended creation:**  
  *Analysis:* Rejected. An immediate `cmd.Start()` followed by `AssignProcessToJobObject` creates a microscopic (~0.1ms to 2ms) window where a rapid child could theoretically spawn a detached grandchild. While `yt-dlp` startup time is ~100ms before `ffmpeg` is ever invoked, suspended creation (Option B) completely eliminates this window down to zero executed opcodes.

**Conclusion:** **Option B (`CREATE_SUSPENDED`) was implemented**. It provides mathematically zero executed opcodes before containment while retaining seamless compatibility with Go's `exec.Cmd` stdio piping.

### 18.3 The Race Analysis & Proof
- **Zero-Opcode Containment Window:** Because the root process is suspended upon creation, it is impossible for application code to execute prior to `AssignProcessToJobObject`.
- **Kernel Inheritance of Descendants:** The Job Object is configured without `JOB_OBJECT_LIMIT_BREAKAWAY_OK` and without `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK`. By Windows kernel semantics, every descendant process created by any process inside the Job Object is automatically and unconditionally placed into the same Job Object.
- **`KILL_ON_JOB_CLOSE` Containment:** The Job Object is configured with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. Even if the parent process exits or attempts to orphan a grandchild, closing the Job Object handle automatically terminates all living descendants in the tree.
- **Empirical Evidence:** Proved by `TestProcessSupervisor_AdversarialEarlySpawn`:
  1. *ConcurrentGrandchild:* Parent immediately spawns grandchild on first instruction; terminating parent tree terminates both parent and grandchild.
  2. *OrphanedGrandchild:* Parent spawns grandchild and immediately exits; when parent's `proc.Wait()` finishes and closes the tree, the Windows kernel automatically terminates the orphaned grandchild via `KILL_ON_JOB_CLOSE`.

### 18.4 Assignment-Failure Cleanup Semantics
If Job Object assignment or resumption fails:
1. `cmd.Process.Kill()` is called immediately on the suspended process.
2. `cmd.Wait()` is called immediately to reap the process handle and eliminate zombies.
3. `tree.close()` closes the Job Object.
4. Because the child was suspended throughout, **no child or grandchild could ever have been created**.
5. The supervisor registry remains completely clean (`ActiveCount() == 0`, `Get(spec.ID) == nil`).
6. The caller receives an explicit, typed error wrapped in `ErrProcessTreeAttach`.
- **Empirical Evidence:** Proved by `TestProcessSupervisor_ContainmentFailureCleanup`.

### 18.5 Context Cancellation Ownership Model
To avoid competing goroutines and race conditions during cancellation:
1. **Single Cancellation Owner:**
   - If `cmd` was created with `exec.CommandContext` (`cmd.Cancel != nil`), Go's standard library runtime already owns the context watcher goroutine. `StartOwned` overrides `cmd.Cancel = func() error { return proc.Terminate() }`. The supervisor does **not** launch a duplicate watcher.
   - If `cmd` was created with `exec.Command` (no context, `cmd.Cancel == nil`) and a non-nil `ctx` was passed to `StartOwned`, the supervisor launches exactly one dedicated watcher goroutine tied to `ctx.Done()`.
2. **Idempotence:** `proc.Terminate()` is protected by `termOnce sync.Once`. Multiple concurrent calls from runtime context, supervisor shutdown, or manual API calls are completely safe.
3. **Wait Memoization:** `proc.Wait()` is protected by `waitOnce sync.Once`. Multiple concurrent callers receive the memoized exit error without racing on `cmd.Wait()`.
- **Empirical Evidence:** Proved by `TestProcessSupervisor_ContextCancellationTreeKill` and `TestProcessSupervisor_NoDoubleKillRace` (20 parallel goroutines calling `Terminate`, `Wait`, and `TerminateAll` without deadlocks or panics).

### 18.6 Non-Windows Behavior & Cross-Platform Status
- **POSIX Implementation (`tree_unix.go`):**  
  Uses process groups (`cmd.SysProcAttr.Setpgid = true`) in `setup()`, and terminates the entire process group in `terminate()` via `syscall.Kill(-cmd.Process.Pid, syscall.SIGKILL)`.

## 21. Final Context-Cancellation Ownership Verification

### 21.1 Previous CommandContext & `cmd.Cancel` Behavior
In earlier iterations:
- Commands constructed via Go standard library's `exec.CommandContext(ctx, ...)` set `cmd.Cancel` internally to a closure invoking `c.Process.Kill()`.
- When `cmd.Start()` runs, Go launches an internal runtime goroutine (`c.watchCtx(ctx)`) that invokes `cmd.Cancel()` upon `ctx.Done()`.
- If `ProcessSupervisor` attempted to post-hook or race alongside this mechanism, two competing goroutines would attempt to terminate the process: Go's direct-child killer (which misses grandchildren like `ffmpeg` on Windows) and `ProcessSupervisor`'s tree terminator.
- Furthermore, mutating `cmd.Cancel` or lifecycle fields after `cmd.Start()` is unsafe and subject to runtime data races.

### 21.2 Exact `cmd.Cancel` Mutation Timing Discovered
An audit of the process lifecycle established that:
1. `exec.Cmd.Start()` in the Go standard library evaluates `if c.Cancel != nil { go c.watchCtx(c.ctx) }`.
2. If `cmd.Cancel` is set to `nil` **prior to `cmd.Start()`**, Go's runtime **never** launches `c.watchCtx`.
3. In `Supervisor.StartOwned`:
   - `cmd.Cancel = nil` is explicitly executed **before** `cmd.Start()`.
   - **Zero fields** of `exec.Cmd` (`cmd.Cancel`, `cmd.WaitDelay`, etc.) are modified after `cmd.Start()`.
   - This completely suppresses the standard library's direct-child kill routine and guarantees zero post-Start mutation races.

### 21.3 Final Supervised-Command Construction
In accordance with Ponytail / YAGNI:
- Supervised long-running tool commands (e.g. `yt-dlp` download subprocess in `internal/engine/ytdlp/ytdlp.go`) are constructed using plain `exec.Command(...)`:
  ```go
  cmd := exec.Command(e.ytdlpPath, args...)
  proc, err := supervisor.StartOwned(ctx, cmd, process.ProcessSpec{...})
  ```
- Short-lived inspect probes (`analyzer.go`, `ToolManager` probes) continue using `exec.CommandContext` because they are bounded by independent timeouts and intentionally live outside `ProcessSupervisor`.
- If a caller passes an `exec.Cmd` created via `CommandContext` to `StartOwned`, `cmd.Cancel = nil` safely suppresses Go runtime's direct-child killer.

### 21.4 Final Cancellation Ownership Model
Exactly **one** component owns process-tree cancellation: `ProcessSupervisor`.
```
Context Cancellation (ctx.Done())
              ↓
ProcessSupervisor Single Watcher Goroutine
              ↓
   proc.Terminate() (idempotent via sync.Once)
              ↓
tree.terminate() (windows.TerminateJobObject / POSIX kill -PGID)
              ↓
Atomic Kernel Tree Termination (Parent + Descendants)
```
- There are no competing goroutines.
- `proc.Terminate()` is strictly idempotent (`termOnce sync.Once`).
- `proc.Wait()` is strictly memoized (`waitOnce sync.Once`).

### 21.5 Four-Phase Cancellation Lifecycle
1. **Phase A (Already Cancelled Pre-Start):**
   If `ctx != nil && ctx.Err() != nil` at entry to `StartOwned`, the method immediately returns `nil, ctx.Err()`. No process tree is allocated, `cmd.Start()` is never called, and **zero OS processes are spawned**.
2. **Phase B (Cancelled During Startup While Suspended):**
   `tree.setup(cmd)` creates the process in a suspended state (`CREATE_SUSPENDED`). It is assigned to the Job Object and verified via `IsProcessInJob`. Before `resumeProcess` is called, `tree.attach` checks `ctx.Err()`. If cancelled, `tree.attach` aborts and returns `ctx.Err()` **without resuming execution**. `StartOwned` immediately calls `cmd.Process.Kill()` and `cmd.Wait()`, closing the tree. **Zero opcodes of application code executed**, and zero descendants were ever created.
3. **Phase C (Cancelled Immediately Post-Resume):**
   If `ctx.Err() != nil` occurs immediately following thread resumption, `StartOwned` terminates the tree via `proc.Terminate()`, reaps the process via `proc.Wait()`, and returns `nil, ctx.Err()`. Zero active entries remain in the registry.
4. **Phase D (Cancelled During Normal Execution):**
   The single watcher goroutine unblocks on `<-ctx.Done()`, invokes `proc.Terminate()`, and terminates the Job Object. When the process finishes, `proc.Wait()` closes `proc.doneChan`, and the watcher exits cleanly without hanging or leaking.
