## 3. Pre-Code Gap Analysis & Crash Window Mapping

In GoDownloader V0.7.2, engine completion and filesystem finalization operated without a durable journal:

1. **`TypeMedia` (yt-dlp)**:
   - Downloaded media files directly into a temporary per-job `WorkDir`.
   - `MoveOrCopyFile` moved the media file from `WorkDir` to user-selected `DestinationDir`.
   - Standalone subtitle sidecars (`.srt` / `.vtt`) were promoted to `DestinationDir`.
   - Job database row was updated to `StatusCompleted`.
   - `WorkDir` was wiped via `CleanupWorkDir`.
2. **Identified Crash Windows**:
   - **Crash during file movement (`MoveOrCopyFile`)**: Destination partially copied or partially renamed; source still in `WorkDir`; DB still in `StatusDownloading`/`StatusProcessing`. On restart, V0.7.2 marked the media job as failed ("Media download was interrupted by application restart"), leaving orphaned staging files and/or partial destination files.
   - **Crash after file movement, before DB commit**: Destination file was fully valid on disk, but DB was not updated. On restart, V0.7.2 discarded the download and marked it failed, potentially allowing `CleanupStaleWorkDirs` to wipe artifacts.
   - **Crash between DB commit and `WorkDir` cleanup**: DB marked `StatusCompleted`, but `WorkDir` remained orphaned.
   - **Ambiguous destination files**: If a destination file was pre-existing or corrupted while staging was gone, unguided recovery risked either corrupting user data or claiming false success.

## 4. Scope Actually Implemented

### 4.1 Durable Journal Lifecycle (`finalizeMediaArtifact`)

When a staged media job completes in `UpdateJobFromEngine`, `finalizeMediaArtifact` orchestrates durable multi-phase commitment:

1. **Phase: `prepared`**:
   - Stat staging source file in `WorkDir` to record `ExpectedSize`.
   - Insert durable `FinalizationRecord` into SQLite with initial phase `prepared`.
2. **Phase: `in_progress`**:
   - Update journal phase to `in_progress`.
   - Invoke `m.storageService.FinalizeFile(ctx, srcFile, destinationDir, policy)`.
   - If destination filename was adjusted for collision (e.g. `video (1).mp4`), update `DestinationPath` in journal.
3. **Phase: `validated`**:
   - Validate destination file via `validateArtifactFile(finalPath, expectedSize, digest)`.
   - Update journal phase to `validated`.
   - Update in-memory active job cache and promote subtitle sidecars via `finalizeMediaSubtitles`.
4. **Phase: `db_committed`**:
   - Update `Job` status to `StatusCompleted`, `Progress = 100`, `FinalPath`, `TotalBytes`, and commit to SQLite repository.
   - Update journal phase to `db_committed`.
   - Remove from active jobs, publish `EventJobCompleted`, clean up engine state.
5. **Phase: `cleanup_pending`**:
   - Update journal phase to `cleanup_pending`.
   - Safely clean up `WorkDir` via `m.storageService.CleanupWorkDir(ctx, jobID, workDir)`.
6. **Phase: `complete`**:
   - Update journal phase to `complete` with non-nil `CompletedAt`.
   - Wake scheduler via `m.scheduler.Kick()`.

If `m.execRepo == nil` (e.g. in legacy tests), the method executes identical finalization steps transparently without database journal records, maintaining complete backward compatibility.

### 4.2 Startup Recovery State Machine (`reconcileFinalizationJournal`)

Integrated directly into `Manager.recover(ctx)`:
`m.reconcileFinalizationJournal(ctx)` runs **first**, before `m.repo.ListRecoverable(ctx)` and before `CleanupStaleWorkDirs`.

#### Recovery Decision Matrix

| Phase in Journal | Disk / File Conditions | Action Taken | Resulting Phase & Status |
|---|---|---|---|
| **`prepared`** | `dstValid == true` | Destination was already moved/valid. Skip move, advance to validated, commit DB, cleanup workdir. | `complete`, `StatusCompleted` |
| **`prepared`** | `dstValid == false && srcExists == true` | Movement did not start or failed before move. Resume `FinalizeFile` from source, validate, commit DB, cleanup workdir. | `complete`, `StatusCompleted` |
| **`prepared`** | `dstValid == false && srcExists == false` | Staging file missing before movement started. Mark journal failed; fail job. | `failed`, `StatusFailed` |
| **`in_progress`** | `dstValid == true` | Movement actually completed before crash. Skip move, advance to validated, commit DB, cleanup workdir. | `complete`, `StatusCompleted` |
| **`in_progress`** | `dstValid == false && srcExists == true` | Move/copy interrupted mid-transfer. Resume `FinalizeFile` from source according to conflict policy, validate, commit DB, cleanup workdir. | `complete`, `StatusCompleted` |
| **`in_progress`** | `dstExists == true && dstValid == false && srcExists == false` | **Ambiguous / User Destination**: Destination is corrupt or wrong size and source is missing. **DO NOT DELETE DESTINATION FILE**. Preserve user file, mark journal failed, mark job failed. | `failed`, `StatusFailed` |
| **`in_progress`** | `dstExists == false && srcExists == false` | Both source and destination missing. Mark journal failed; mark job failed. | `failed`, `StatusFailed` |
| **`validated`** | `dstValid == true` | Destination validated before crash, but DB commit did not finish. Commit DB to `StatusCompleted`, cleanup workdir. | `complete`, `StatusCompleted` |
| **`validated`** | `dstValid == false && srcExists == true` | Destination deleted or corrupted externally, but source intact. Re-finalize from source, validate, commit DB, cleanup workdir. | `complete`, `StatusCompleted` |
| **`validated`** | `dstValid == false && srcExists == false` | Destination invalid and source gone. Mark journal failed; mark job failed. | `failed`, `StatusFailed` |
| **`db_committed`** | Any | Job already marked completed in DB. Ensure DB `StatusCompleted`, clean up workdir, complete. | `complete`, `StatusCompleted` |
| **`cleanup_pending`**| Any | Workdir cleanup interrupted. Clean up workdir with safety marker validation, complete. | `complete`, `StatusCompleted` |
| **`complete` / `failed`** | Any | Terminal records. Ignored (no-op). | Unchanged |

## 5. Architectural Invariants Preserved

1. **Non-Atomic Multi-System Invariant**: Filesystem operations and SQLite commits can NEVER be a single atomic transaction. State transitions are strictly phased and durable in SQLite before filesystem mutations.
2. **User Destination Protection Invariant**: If a destination file exists but cannot be validated and the source file is missing, the recovery system **NEVER** deletes or overwrites the destination file. It marks the record failed and preserves the user's filesystem state.
3. **Safety Marker Enforcement**: Cleanup of `WorkDir` during finalization and startup recovery strictly validates the `.godownloader-workdir` marker matching `jobID` before performing recursive deletion.
4. **Startup Sequencing Invariant**: Running `reconcileFinalizationJournal` prior to `ListRecoverable` ensures that jobs successfully finalized on disk have their DB status committed to `StatusCompleted` first. They are never erroneously swept up by `ListRecoverable` and never falsely failed with "Media download was interrupted by application restart."
5. **Idempotence**: Multiple sequential recovery invocations produce identical end states without duplicate side effects, file deletions, or errors.

## 8. Final Artifact Ownership & Workflow Coverage Gate Review

During the final artifact ownership and workflow coverage review gate, five critical questions were investigated and verified:

### 8.1 Destination Ownership vs. Size-Only Validation
- **Identified Risk:** If recovery accepts a destination file solely on size match while staging source is unconsumed, an unrelated pre-existing user file of the exact same size would cause recovery to falsely mark the job complete and delete the real staging download via `CleanupWorkDir`.
- **Architectural Invariant Enforced:** Whenever `srcExists == true` in `prepared` or `in_progress`, recovery **ALWAYS** resumes finalization from source (`m.resumeFinalizationFromSource`). Recovery never assumes ownership of an existing destination file by size alone while the unconsumed staging source is intact.
- Under `ConflictPolicyRename`, the pre-existing user file is preserved untouched and our download is promoted to `name (1).ext`.
- If `srcExists == false` in `prepared`: movement never began; recovery refuses to claim destination on size alone without cryptographic digest verification (`ExpectedDigest`), failing safely to avoid adopting foreign files.

### 8.2 Collision-Renamed Destination Crash Recovery
- **Identified Crash Window:** When `ConflictPolicy == rename` and `name.ext` already exists, `FinalizeFile` chooses `name (1).ext`. If a crash occurred during file movement before SQLite journal update, the journal still had `DestinationPath = name.ext`.
- **Dual Defense Implemented:**
  1. **Proactive Resolution:** In `finalizeMediaArtifact`, `m.storageService.ResolveFinalPath` is called *prior* to inserting the initial `FinalizationRecord`. The journal in SQLite holds `name (1).ext` before any filesystem movement begins.
  2. **Defensive Reconnection:** In `reconcileFinalizationRecord`, if `!srcExists && !dstValid` under rename policy, `findRenamedArtifact` inspects candidate collision filenames (`name (1).ext`, `name (2).ext`, etc.) for size/digest match before failing.

### 8.3 Direct / aria2 and qBittorrent / Torrent Applicability
- **Direct / aria2:** Writes directly into `j.DestinationDir`. GoDownloader performs no staging directory moves for aria2 upon completion. Reattachment recovery operates directly via aria2 daemon GID. **Explicit Classification: `NO JOURNAL REQUIRED FOR CURRENT DIRECT FLOW`**.
- **qBittorrent / Torrent:** Writes directly into `j.DestinationDir`. Seeding and completion state is persisted via `torrentRepo.FinalizeTorrent`. Daemon removal is tracked via `j.EngineCleanupPending` and `processPendingEngineCleanups`. FinalizationJournal is not forced onto direct torrent writes. **Explicit Classification: `NO CODE CHANGE REQUIRED`**.

### 8.4 `db_committed` Phase Ordering
- In both `finalizeMediaArtifact` and `commitAndCleanupFinalization`, `m.repo.Update(ctx, j)` executes *before* `UpdateFinalizationPhase(..., FinalizationPhaseDBCommitted)`. The phase name is strictly truthful.

### 8.5 Subtitle Sidecar Ordering & Idempotence
- `finalizeMediaSubtitles` moves sidecars individually from `WorkDir` to `DestinationDir`. Once moved, they are absent from `WorkDir`. Re-running recovery skips already moved sidecars. Idempotence is structurally guaranteed.

## 9. Final Destination Identity Verification

### 9.1 `findRenamedArtifact` Ownership Finding & Absence of Digest
- **Finding:** Previously, `findRenamedArtifact` inspected candidates `name (1).ext`, `name (2).ext` etc. using `validateArtifactFile(candPath, expectedSize, expectedDigest)`. When `ExpectedDigest == ""`, it evaluated matching file size alone. This allowed an unrelated user file coincidentally matching `ExpectedSize` at an unrecorded collision candidate path to be falsely adopted, destroying staging without cryptographic proof of ownership.
- **Invariant Enforced:** An artifact path that was NOT durably recorded before the crash must **never** be adopted by size alone. In `findRenamedArtifact`, if `expectedDigest == ""`, it immediately returns `"", false`. Reconnection is permitted **only** when `ExpectedDigest` is non-empty and cryptographically verified via SHA-256.

### 9.2 Destination Pre-Resolution & `FinalizeFile` Path Re-Resolution Analysis
- **Finding:** Previously, `finalizeMediaArtifact` and `resumeFinalizationFromSource` called `ResolveFinalPath` to select e.g. `video (1).mp4` and durably stored it in `FinalizationRecord`. However, they subsequently called `m.storageService.FinalizeFile(ctx, srcFile, j.DestinationDir, policy)`. `FinalizeFile` did **not** accept a destination path; it internally called `ResolveFinalPath` a second time.
- **Identified Race Window (TOCTOU):** If an unrelated file appeared at `video (1).mp4` after journal persistence but before file movement, `FinalizeFile` would re-resolve to `video (2).mp4`, moving the artifact to an unjournaled path while the journal remained at `video (1).mp4`.
- **Architectural Invariant Enforced:** *The path durably recorded in the journal before source-removing filesystem mutation is the exact path targeted by that mutation.*

### 9.3 Code Corrections
1. **`MoveOrCopyFileExact(src, dst string, allowOverwrite bool) error`:** Implemented in `internal/storage/conflict.go`. If `dst` exists and `allowOverwrite` is false, it returns `ErrFileConflict` immediately without modifying `dst` or removing `src`.
2. **`IStorageService.FinalizeFileToPath(ctx context.Context, srcPath, exactDestPath string, allowOverwrite bool) error`:** Added to `IStorageService` and implemented in `StorageService`. Targets the exact journaled path without re-running conflict resolution.
3. **`finalizeMediaArtifact`:** Directly calls `FinalizeFileToPath(ctx, srcFile, targetPath, allowOverwrite)`. If a post-resolution collision occurs, it fails safely, preserves staging, and never diverts to an unjournaled path.
4. **`resumeFinalizationFromSource`:** Re-resolves and durably updates `rec.DestinationPath` in SQLite *before* calling `FinalizeFileToPath`.
