## 3. B-1 — root cause (VS, previously VT in the audit)

`cmd/desktop/main.go` created `startCtx, cancelStart := context.WithTimeout(...)`, passed it to `App.Start`, and called `cancelStart()` as soon as startup returned. `App.Start` hands that context to `Manager.StartBackgroundTasks`, so the scheduler loop, progress monitor, network reconciler and tracker runner all exited right after initialization. Queued jobs were never dispatched on the desktop host.

## 4. B-1 — correction

- New `cmd/desktop/core.go`: `startDesktopCore(cfg, dbPath)` constructs the App and starts it under a **process-lifetime** context (`context.WithCancel(context.Background())`). That context is cancelled only by `desktopCore.Shutdown`, which first runs the ordered `App.Shutdown` (tracker → manager loops → process trees → database → ownership locks). Any failure after construction shuts the core down again, so no workers, database handle or lock leak.
- `cmd/desktop/main.go` uses `startDesktopCore` (ownership collision still shows the native collision dialog) and ends with `core.Shutdown(5s)` after `wailsApp.Run()`. `RequestQuit` → `App.Shutdown` stays idempotent.
- Liveness observability (read-only): `Scheduler.Running`, `Monitor.Running`, `Manager.BackgroundWorkers()` (scheduler, monitor, reconciler), and `App.BackgroundWorkers()` (adds the tracker). They are set and cleared inside each loop goroutine.
- Close-to-tray is unchanged: `DesktopLifecycle.HandleWindowClosing` only hides the window and never touches the core.

## 6. D-1 — root cause (VS)

`--diagnostic-smoke` started a second runtime with its own database but the **main application's data directory**. Startup cleanup in that runtime:

- (`Manager.StartBackgroundTasks` → `StorageService.CleanupStaleWorkDirs`) deleted every marked work directory whose job its own (empty) database did not list as active;
- (`mediaauth.Service.CleanupStaleTempFiles`) deleted every `godownloader_cookie_*.txt` export.

In both cases those belonged to the running main instance's in-progress downloads.

## 7. D-1 — correction

Two layers; ignoring files in Git was not used:

1. **Isolated smoke** (`cmd/desktop/smoke.go`): `runDiagnosticSmoke` creates a disposable `os.MkdirTemp` workspace (data dir, download dir and DB inside it), runs `runSmokeInWorkspace`, and removes the workspace. `main.go` still resolves the desktop data root, but no longer runs a runtime against it.
2. **Data-directory cleanup ownership** (`internal/app/lifecycle.go`): `app.New` tries an exclusive `runtimeguard` lock on `<DataDir>/cleanup-owner.runtime.lock`, the same primitive as the per-DB runtime guard (exclusive `CreateFile` share mode 0 on Windows; `flock` on Unix). Only the holder runs the startup work-dir and cookie-export cleanup (`Manager.SetSharedDataCleanupAllowed`). A runtime that cannot prove ownership logs that cleanup is disabled and deletes nothing. The lock is released in `App.Shutdown` (and on construction failure). No processes are inspected or terminated.

## 9. H-1 — linearization analysis (VS)

Steps involved:

- **Claim:** the scheduler's `TryAcquire` lease plus the `inFlight` reservation.
- **Persist running state:** `QUEUED → DOWNLOADING`.
- **Resources:** the transfer lease, keyed by job ID.
- **Engine start:** `eng.Start`, `StartDownload` or `Resume`.
- **Cancel:** `CANCELLED`.

Before the fix, both writers performed unconditional full-row writes from stale snapshots, and Cancel released the lease without knowing whether a dispatch was mid-start.

**Linearization point chosen:** the persisted job `status` column. Each lifecycle writer commits **only if the status is still what it observed** (a single SQL `UPDATE … WHERE id=? AND status=?`), so exactly one of dispatch or cancel wins. The loser re-evaluates (Cancel) or undoes its side effects (dispatch).

**Lease release** has exactly one owner, decided under `Manager.mu`, and is never held across subprocess or network calls:

- dispatch registers `dispatching[jobID]` before reading the job;
- a Cancel that commits while that flag is set records `cancelledDuringDispatch[jobID]` and leaves the release to `endDispatch`, which runs after the dispatch has stopped any engine it started;
- otherwise Cancel releases immediately.

`ReleaseTransfer` is idempotent per job ID and the job is terminal, so a duplicate release by the scheduler is harmless.

## 10. H-1 — correction

- `IJobRepository.UpdateIfStatus(ctx, j, expected) (bool, error)`: the SQLite implementation shares the existing full-row update (`updateJob`) with an added `AND status=?`. `Update` is unchanged.
- `Manager.dispatchQueuedJob`:
  - `beginDispatch`/`endDispatch` bracket the dispatch;
  - terminal jobs return `DispatchHandledError`;
  - `observed := j.Status`;
  - the torrent TotalBytes repair and the final DOWNLOADING write are conditional on `observed`;
  - a pre-start check skips the engine start if a cancel already committed;
  - on a lost final CAS, `abandonLostDispatch` stops the engine it started (cancel if the job is cancelled, deleted or failed; pause if it moved to another live state such as PAUSED), cleans a cancelled media work dir, and returns `DispatchHandledError`, so the scheduler releases the lease.
- `Manager.persistDispatchFailure`: the FAILED/PAUSED write is conditional; a lost CAS returns `DispatchHandledError` without publishing FAILED.
- `Scheduler.dispatchSingle`: the generic engine-failure persistence (FAILED/PAUSED from the pre-dispatch snapshot) is conditional; a lost CAS releases the lease and publishes nothing.
- `Manager.cancel`:
  - the CANCELLED write is conditional on the observed status;
  - on loss it re-evaluates from the authoritative row (bounded by the existing `maxCancelAttempts = 3`, then returns a retryable `ErrInvalidJobState`), so a dispatch that already persisted DOWNLOADING with an engine ID is cancelled in the engine;
  - the final release goes through `releaseCancelledJob`.
- Test doubles that inject `Update` failures now apply the same injection to `UpdateIfStatus`; failure semantics are unchanged.

## 13. H-2 — root cause (VS; VT in the audit with the real binary)

`AnalyzeWithPolicy` ran `exec.CommandContext(...).Output()`. FND-4B exempted analysis on the premise "no descendants spawned". That premise is false for the official Windows `yt-dlp.exe`: it is a PyInstaller onefile executable that re-executes itself as a child process. Cancelling killed only the root, so:

- the child survived, still holding the binary image and the stdout pipe;
- `Output()` blocked on that pipe;
- the UsageGate and analysis permit stayed held until the orphan exited.

## 14. H-2 — correction

- `internal/engine/ytdlp/analyzer.go` → `runAnalysisProcess`:
  - the analysis runs through the engine's `ProcessSupervisor.StartOwned` (created suspended, assigned to a Job Object with `KILL_ON_JOB_CLOSE`, then resumed), with a unique ID `ytdlp-analysis-N`, `Purpose: "analysis"`;
  - output is collected into buffers;
  - cancellation, deadline and supervisor shutdown terminate the whole tree through the supervisor's sole context watcher;
  - `cmd.WaitDelay` (2 s) bounds pipe draining when a descendant holds the pipe after a successful root exit; that case is treated as success because the root's output is complete;
  - the function returns only after `ManagedProcess.Wait` has torn the tree down. The deferred UsageGate release and auth temp-file cleanup in `AnalyzeWithPolicy`, and the caller's analysis permit, therefore run strictly after no process of the analysis remains;
  - the engine mutex is held only to read the supervisor, never across execution.
- `internal/process/tree_windows.go`:
  - `terminate()` and `close()` now call `terminateJobAndWait`. It opens SYNCHRONIZE handles **only to the job's own member processes** (from `JobObjectBasicProcessIdList`, each confirmed with `IsProcessInJob` so a recycled PID is never awaited), calls `TerminateJobObject`, and waits, bounded at 5 s, until each member's process object is signaled and the job reports zero active processes;
  - `close()` does this only when the job still has active members, i.e. descendants the root left behind;
  - there is no system-wide process scan, no termination by executable name, and nothing outside the job is affected;
  - this also strengthens the download path, which uses the same tree.

An intermediate version that waited only on the job's ActiveProcesses counter was observed to return while a terminated process object was not yet signaled. Waiting on the member handles closed that gap.

**Download-path side effect found and resolved (VT).** After the tree change, the existing `TestEngine_Download_CookieAuth_CancellationCleanup_RealChild` failed 8 of 20 runs.

- **A/B check:** with the HEAD `tree_windows.go` it passed 20/20.
- **Diagnosis:** a disposable probe (deleted afterwards) that records the cookie `Remove` result found that the product **does** delete the cookie export on every cancel (15/15, `Remove` succeeded).
- **Cause:** the test double `mockAuthProvider` set `cleanupRan` *before* removing the file. Because `Cancel` now returns in step with the download goroutine's teardown, the test could observe "cleanup ran" while the file still existed.
- **Fix:** the double sets the flag after its removal (`internal/engine/ytdlp/auth_test.go`). Afterwards the test passed 20/20, and the full `internal/engine/ytdlp` package passed 3 single and 5 repeated (`-count=5`) runs.
- **Unexplained:** one package-level run immediately after the fix reported `FAIL` without its output being captured. It was not reproduced in any of the 8 subsequent package runs and remains unexplained.

## 22. Progress-monitor race — investigation and fix

**Investigation (VS).**

- `Monitor.tick` takes copies of the active jobs (`GetActiveJobs`), queries each engine, then calls `Manager.UpdateJobFromEngine(snapshot, status)`.
- Every branch of `UpdateJobFromEngine` persisted the **whole row from that snapshot** with an unconditional `repo.Update`. That covers progress, PROCESSING, PAUSED, SEEDING, COMPLETED, FAILED, CANCELLED and the media-validation failures.
- The progress branch also re-inserted the snapshot into `activeJobs` unconditionally and published it.
- So a tick that snapshotted DOWNLOADING before a Cancel committed could:
  - write DOWNLOADING over CANCELLED;
  - put the job back in the active set, where the monitor keeps polling an engine nobody owns;
  - announce it to the UI after its cancellation event.
- COMPLETED and FAILED rows were equally exposed.
- Equivalent writers in the same flow, also confirmed:
  - `finalizeMediaArtifact`'s COMPLETED commit;
  - `failJobWithReason`;
  - the monitor's own `recordFailure`, which checked for a terminal state and then wrote unconditionally.

**Fix (smallest repository-level mechanism; no second state machine):**

1. **`Manager.persistObservedState(ctx, j, observed)`** reuses the existing `UpdateIfStatus` CAS.
   - It commits only while the row still holds the state the snapshot observed.
   - If the row moved to another *engine-observable* state (DOWNLOADING, PROCESSING, SEEDING), e.g. a snapshot lagging a PROCESSING write, it retries once against that state, so legitimate completions are never lost.
   - It never writes over CANCELLED, COMPLETED, FAILED, PAUSED, QUEUED or a deleted row.
   - All writes in `UpdateJobFromEngine`, `finalizeMediaArtifact`, `failJobWithReason` and `Monitor.recordFailure` go through it.
   - Startup recovery passes freshly read rows, so its behaviour is unchanged.
2. **A per-job state lock (`Manager.jobStateLock`)** serializes three things for the same job:
   - applying one engine observation;
   - Cancel's commit-remove-announce section;
   - dispatch's register-and-announce tail.

   It orders the active set and the event stream. It is per job, not global, and is never held while an engine is started or cancelled. The monitor path holds it across its own short persistence work only.
3. **`replaceActiveIfPresent`.** Observations refresh only jobs that are still active and never re-insert one. Ephemeral progress events are published only for active jobs. A won PROCESSING write now also refreshes the active entry (previously it did not, so the in-memory copy lagged).
4. **Dispatch tail.** Under the state lock, a dispatch whose job was cancelled after its DOWNLOADING commit neither registers nor announces it. `endDispatch` therefore no longer re-announces the cancellation (Part I did that, producing a duplicate event); it only performs the deferred lease release.

**Lost finalization commit.** If a lock-free transition (pause or delete) beats the media COMPLETED commit, the validated artifact stays at its final path and the journal records `failed` ("job state changed before commit"). Startup recovery skips `failed` records (`reconcileFinalizationRecord`), so the job is not resurrected at restart.

## 23. Reconciliation bypass — confirmed and fixed (same runtime flow)

**Finding (VS).** When a dispatch started an engine but its DOWNLOADING write failed, the scheduler keeps a **dirty reservation** and the lease, and reconciles every round.

- `reconcileExternalExecution` read the row, queried the engine, and wrote DOWNLOADING, PROCESSING or SEEDING **unconditionally**, even over a row it had itself read as CANCELLED. It then re-activated the job.
- `reconcileStatePersistence` wrote FAILED or PAUSED over CANCELLED.
- Because the engine ID was never persisted, a Cancel in that window could not reach the engine. It also released the lease while that engine still ran.

Part I's Section 19 had wrongly stated that this path was safe; that statement is corrected above.

**Fix:**

- Both reconcilers treat a terminal row as authoritative. The external one stops the engine its reservation started, using the TOR-EXT-guarded engine `Cancel`, and only then releases the reservation and lease. The state one just releases.
- Their writes are conditional on the observed state; a lost write retries next round.
- The reconciler's activation goes through `Manager.addActiveIfLive`, which re-checks the row under the state lock.
- `releaseCancelledJob(jobID, observed)` leaves the lease to the scheduler when the cancellation beat a not-yet-running state (QUEUED/PAUSED) while the scheduler still holds the job's reservation. Every scheduler outcome for that reservation then releases the lease itself, the reconciler only after stopping the engine:
  - handled skip;
  - generic failure;
  - dispatch-time skip of a cancelled job;
  - dirty reconciliation.

## 25. H-1 dispatch/monitor composition proof (VS + VT)

Linearization points:

- **Job status:** one CAS per transition; dispatch, Cancel, monitor, finalization and reconcilers all write conditionally.
- **Active set and events:** the per-job state lock.
- **Lease:** exactly one releasing owner. Ownership moves from the scheduler reservation (selection) to the dispatch (`dispatching`), then to the active transfer (DOWNLOADING committed), then to whichever of Cancel, the monitor's terminal transition, `endDispatch` or the scheduler outcome ends it. Each release happens only after the engine has been stopped or was never started.

| Concern | Result |
|---|---|
| Cancel wins | Engine stopped by `abandonLostDispatch`; lease released after it |
| Dispatch wins | Cancel re-evaluates, reaches the engine (engine ID persisted), then releases |
| Engine start failure | Scheduler CAS; no FAILED over CANCELLED |
| Queue deletion | Unchanged; Cancel deletes after its commit |
| CAS failure | Handled as a lost transition, never as an error resurrecting state |
| Duplicate Cancel | `ValidateTransition` refuses CANCELLED→CANCELLED; no side effects (VS) |
| Monitor registration | Only via the dispatch tail or `addActiveIfLive`; never re-inserted by observations |
| qB foreign tasks | All engine stops use the existing qB engine `Cancel`/`Pause` with TOR-EXT ownership guards; ownership rules unchanged |
| aria2 / yt-dlp | Covered by the fake-engine tests (aria2 semantics) and the supervised yt-dlp path (Part I §14) |
| Shutdown / recovery | `Manager.Stop` and recovery paths are unchanged; recovery's `failJobWithReason` passes fresh rows (identical behaviour) |

## 28. H-2 acceptance (VS + VT)

`tree_windows.go` creates processes suspended and assigns them to a Job Object (`KILL_ON_JOB_CLOSE`), and owns children and grandchildren. Teardown:

1. opens SYNCHRONIZE handles to **job members only** (`JobObjectBasicProcessIdList`, each confirmed with `IsProcessInJob`);
2. calls `TerminateJobObject`;
3. waits, bounded at 5 s, for every member to be signaled and the job to report zero active processes;

There is no global scan, no termination by name, and no process outside the job is touched. `StartOwned` failure paths close the tree (existing FND-4B behaviour).
