## 1. Executive Summary

FND-5B introduces a concurrency-safe, in-memory `ResourceGovernor` to GoDownloader to prevent engine oversubscription, manage multi-dimensional runtime capacity, eliminate head-of-line blocking, and decouple network transfer concurrency from post-processing and seeding phases.

Prior to FND-5B, the scheduler enforced only a coarse global limit (`CountDownloading() + inFlight >= max_concurrent_downloads`). If multiple downloads used the same engine (such as yt-dlp or qBittorrent), all active slots could saturate a single engine, leading to process contention, rate-limiting, and UI freezes. Furthermore, when a download completed and entered FFmpeg processing or torrent seeding, it continued counting against the network transfer limit, preventing waiting queued downloads from starting.

FND-5B delivers:
1. **Multi-Dimensional Resource Governor:** A dedicated, in-memory `ResourceGovernor` that atomically arbitrates global network transfer capacity and per-engine concurrency.
2. **Head-of-Line Non-Blocking Candidate Scan:** The scheduler scans eligible runnable jobs in strict FND-5A priority/aging order. If the highest-ranked candidate requires an engine whose capacity is saturated, the governor rejects that specific candidate, allowing lower-ranked candidates with available engine capacity to dispatch without altering or dropping the blocked candidate's queue position.
3. **Phase-Aware Capacity Hand-off:** When a torrent transitions from `DOWNLOADING` to `SEEDING`, the governor immediately releases its network transfer and engine permits, unblocking queued network transfers. When a media download enters `PROCESSING` (FFmpeg merge/remux), it safely retains its transfer and engine permit until process exit.
4. **Resilient Ephemeral Architecture:** In accordance with target architectural principles, governor state is strictly in-memory and reconstructible on startup from durable active jobs during recovery, avoiding fragile persisted wait reasons or database schema migrations.

## 2. Inventory & Classification of Resources

| Dimension | Classification | Limits & Enforcement |
|---|---|---|
| **Global Transfer** | Core Resource | Managed by governor global transfer limit (default: 3, dynamically driven by `SettingsService.EffectiveMaxConcurrentDownloads`). |

| **Media Subprocess** | Unified | Media downloads consume `Global Transfer` + `Engine: ytdlp` for full subprocess lifetime. Separate artificial media semaphore is YAGNI and omitted. |

## 4. Ponytail & YAGNI Architecture Decisions

1. **Zero Database Schema Migrations:**
   No SQLite columns (`wait_reason`, `waiting_for_engine`, etc.) or permit tables were added. Wait states are transient and ephemeral; persisting them introduces distributed state drift across crashes.
2. **Ephemeral In-Memory State:**
   Governor leases and counters reside entirely in RAM. On application startup, `Manager.recover()` reattaches running engine tasks and invokes `ResourceGovernor.ReconstructJob(j)`, rebuilding the ground truth before the scheduler starts.
3. **Leaf Lock Thread-Safety:**
   `ResourceGovernor.mu` protects only in-memory primitive counters and lease maps. It NEVER invokes external methods, database operations, engine calls, or other subsystem mutexes. It is guaranteed to be a leaf lock, making deadlocks structurally impossible.
4. **No Artificial Media Semaphore:**
   A distinct "media" semaphore was rejected as redundant (YAGNI). Media downloads naturally require a global transfer slot and an engine slot (`ytdlp`). Media post-processing naturally requires a `Processing` slot.
5. **Preservation of FND-5A Determinism:**
   Candidate evaluation preserves FND-5A strict total ordering (`CompareQueuedJobs` / `RankQueuedJobs`). Bypassing blocked candidates does not modify or demote their queue positions.

## 5. In-Memory ResourceGovernor Design

### Core Data Structures (`internal/job/governor.go`)

```go
type ResourceRequirements struct {
    Engine string // "ytdlp", "qbittorrent", "aria2", etc.
}

type ResourceLease struct {
    JobID      string
    Engine     string
    AcquiredAt time.Time
}

type ResourceGovernorConfig struct {
    GlobalTransferLimit int
    EngineLimits        map[string]int
}

type ResourceGovernor struct {
    mu                  sync.Mutex
    globalLimitFn       func() int
    globalTransferLimit int
    engineLimits        map[string]int
    activeTransfers     int
    activePerEngine     map[string]int
    leases              map[string]*ResourceLease
}
```

### Atomic Multi-Resource Admission
`TryAcquire(jobID string, req ResourceRequirements)` verifies all required dimensions under a single mutex lock. If any required capacity (e.g. engine limit or global transfer limit) is exhausted, the call returns `ErrResourceCapacityExceeded` with zero counter increments.

## 6. Head-of-Line Non-Blocking Candidate Scan

The scheduling loop in `Scheduler.schedule()` previously evaluated only `queueRepo.NextRunnable(now)`. If the top candidate was blocked by an engine limit, the scheduler stopped, causing head-of-line blocking.

Under FND-5B:
1. `IQueueRepository.ListRunnable(ctx, evalTime)` returns all runnable queued jobs sorted strictly by FND-5A total ordering (`RankQueuedJobs`).
2. `Scheduler.schedule()` iterates through candidates in order:
   - Skips jobs already in flight.
   - Evaluates `governor.TryAcquire(candidate.JobID, req)`.
   - If `TryAcquire` fails (e.g. `engine "ytdlp" capacity full`), the scheduler continues to the next candidate.
   - If `TryAcquire` succeeds, the candidate is reserved and dispatched.
3. The blocked job remains in `job_queue` at its exact position and priority. As soon as its required engine capacity is freed, the next scheduler kick admits it.

---

## 7. Run Now & Resource Limit Interaction

Run Now jobs (`position <= 0`) are sorted to the very front of the candidate list by FND-5A policy. When evaluated by the scheduler:
- If required resources are available, the Run Now job dispatches immediately.
- If required resources (global transfer limit or specific engine limit) are saturated, the governor rejects admission.
- The Run Now job **remains queued at top precedence** and does NOT exceed hard concurrency boundaries.
- As soon as any active job releases a slot, the next kick immediately admits the waiting Run Now job.

---

## 8. Phase Transitions & Capacity Release

When a torrent download completes and begins seeding, or a media download enters post-processing:
1. **Torrent Seeding Hand-off:** When `UpdateJobFromEngine` detects transition to `StatusSeeding`, it immediately calls `m.resourceGovernor.Release(j.ID)` to release the global network transfer permit. It then calls `m.scheduler.Kick()`, unblocking waiting queued downloads while seeding continues in the background.
2. **Media Subprocess Post-Processing:** When `UpdateJobFromEngine` detects transition to `StatusProcessing` (FFmpeg remux/merge inside yt-dlp), the job safely retains its Global Transfer + `ytdlp` engine lease until terminal completion (`StatusCompleted`, `StatusFailed`, `StatusCancelled`), accurately reflecting active CPU and subprocess resource consumption.
3. The scheduler detects the freed transfer slot from seeding transitions and immediately dispatches the next eligible queued download.

---

## 9. Lifecycle Releases

Every exit path from the active state guarantees release of held governor capacity:
- **Completion / Failure / Cancellation:** `m.removeActive(id)` calls `gov.Release(id)`.
- **Pause:** `m.Pause(ctx, id)` removes active and releases the lease; kicks the scheduler. If engine pause fails, the job remains active and the lease is safely retained.
- **Dispatch Failure:** `scheduler.dispatchSingle` releases the lease if preflight or engine start fails.
- **Reconciliation Failure:** `scheduler.reconcileStatePersistence` releases the lease once the terminal state is persisted.

All releases are idempotent: double-releasing or releasing an unknown ID is a safe no-op that never drives counters below zero.

---

## 10. Startup Reconstruction

During server boot:
1. `Manager.StartBackgroundTasks(ctx)` runs `m.recover(ctx)`.
2. `recover()` reattaches running engine tasks (`DOWNLOADING`, `PROCESSING`, `SEEDING`) and adds them to `m.activeJobs`.
3. Immediately following recovery, `StartBackgroundTasks` loops over `m.activeJobs` and invokes `m.resourceGovernor.ReconstructJob(j)`.
4. `ReconstructJob` rebuilds active leases for `StatusDownloading` and `StatusProcessing`, tracking them even if they exceed configured limits.
5. Only after reconstruction is complete does the scheduler start and kick (`m.scheduler.Start(ctx)`).
6. Result: Zero oversubscription on restart. If downloads were running before restart, no queued work will dispatch until capacity is freed.

## 15. Final Resource-Lifetime & Phase-Admission Verification

### A. Comprehensive Permit Lifecycle Map

```
                     +---------------------------------------+
                     |        Scheduler.schedule()           |
                     |  Iterates queueRepo.ListRunnable()    |
                     +-------------------+-------------------+
                                         |
                       governor.TryAcquire(jobID, req)
                                         |
                      [Acquired? Atomic All-or-Nothing]
                                /                 \
                             No                    Yes
                             /                       \
        [Bypass candidate: bleibt QUEUED]       [dispatchJob()]
        [Scan lower-ranked candidate]                  |
                                                       v
                                            +---------------------+
                                            | Status: DOWNLOADING |
                                            | Lease held:         |
                                            | - Global Transfer   |
                                            | - Engine (e.g. yt)  |
                                            +----------+----------+
                                                       |
                       +-------------------------------+-------------------------------+
                       |                               |                               |
           [yt-dlp FFmpeg post-processing]   [Torrent 100% complete]       [Pause / Cancel / Terminal]
                       |                               |                               |
                       v                               v                               v
             Status: PROCESSING                Status: SEEDING              removeActive(jobID)
             Transfer lease RETAINED         gov.Release(jobID)             gov.Release(jobID)
             until process exit              Transfer permit freed!         Capacity restored!
             (No false pre-admission)        scheduler.Kick()               scheduler.Kick()
                       |                               |                               |
                       +-------------------------------+-------------------------------+
                                                       |
                                                       v
                                             Capacity Safely Restored
                                             Zero Leak / Zero Negative
```

1. **Acquisition:** Exclusively in `Scheduler.schedule()`. Candidates are scanned in strict FND-5A total ordering (`queueRepo.ListRunnable()`). Before starting any engine or touching files, `governor.TryAcquire(candidate.JobID, req)` atomically acquires the global transfer permit and engine permit under a single mutex.
2. **Holding:** While active, leases are tracked in `ResourceGovernor.leases[jobID]` in memory.
3. **Phase Hand-off / Release Paths:**
   - **Torrent Seeding:** When qBittorrent reaches 100% and enters `StatusSeeding`, `Manager.UpdateJobFromEngine()` calls `gov.Release(j.ID)`. The download transfer permit is immediately freed, and `m.scheduler.Kick()` admits waiting downloads while seeding continues in the background.
   - **Media Processing:** `yt-dlp` jobs entering `StatusProcessing` (FFmpeg post-processing) continue to hold their existing transfer and engine lease until terminal completion (`StatusCompleted`, `StatusFailed`, or `StatusCancelled`).
   - **Terminal Exit:** In `removeActive(id)`, `gov.Release(id)` is invoked, atomically restoring capacity.
   - **Pause / Cancellation:** `Manager.Pause()` and `Manager.Cancel()` remove the job from active and release governor capacity. For `yt-dlp`, `Cancel` awaits process reaping (`proc.Wait()`) before releasing permits.
   - **Preflight / Dispatch Failure:** In `scheduler.dispatchSingle()`, failure during preflight or engine start calls `s.releaseGovernorLease(candidate.JobID)`, rolling back capacity and kicking the scheduler.

### B. Processing Capacity Hard-Limit Audit & Classification
- **Investigative Finding:** `yt-dlp` executes as a single external process that internally executes FFmpeg as a child subprocess during video/audio merging and remuxing. `StatusProcessing` is detected post-facto via stdout stream parsing (`[Merger]` / `[ExtractAudio]`). GoDownloader has no pre-execution hook prior to FFmpeg invocation and cannot intercept or block FFmpeg from starting.
- **Architectural Principle:** A resource dimension can be called a **HARD limit ONLY if acquired before the governed work begins**. Post-facto observation cannot be labeled as hard admission control.
- **Decision:** Dedicated `Processing` capacity as an independent hard admission limit is **EXPLICITLY DEFERRED** under YAGNI.
- **Safety Invariant:** `yt-dlp` jobs conservatively hold their Global Transfer + `ytdlp` Engine lease for their **complete process lifetime** (from subprocess launch until exit). This bounds CPU, process tree count, and memory without making false claims of pre-admission control.

### C. Seeding Capacity Hard-Limit Audit & Classification
- **Investigative Finding:** `qbittorrent` runs as an external daemon (`ExternalUserManaged`). When a torrent reaches 100% completion, qBittorrent transitions into seeding autonomously; GoDownloader only discovers the state change on the next polling interval.
- **Decision:** Dedicated `Seeding` capacity as an independent hard admission limit is **EXPLICITLY DEFERRED** under YAGNI.
- **Safety Invariant:** Upon detecting `StatusSeeding`, GoDownloader calls `gov.Release(j.ID)`, freeing the scarce download transfer permit so waiting downloads can dispatch immediately.

### D. Pause & Cancel Process Safety & Release Ordering
- In `internal/engine/ytdlp/ytdlp.go`, `Cancel()` sends `SIGKILL` to the process tree and calls `proc.Wait()`, ensuring the process tree is fully reaped and dead before `Manager.Cancel()` removes the job and releases the governor lease.
- In `internal/job/manager.go`, `removeActive(id)` atomically deletes from `activeJobs`, releases the governor lease, and returns whether an active job or lease was released.
- In `internal/job/scheduler.go`, `releaseGovernorLease(jobID)` kicks the scheduler **only if** `gov.Release` returned `true`, preventing redundant scheduler churn and hot loops.

### E. Single Authority for Global Transfer Capacity
- When `s.governor != nil`, the `ResourceGovernor` is the single, authoritative gatekeeper for global transfer permits via atomic `CanAdmit` and `TryAcquire` checks. Coarse database download counts are bypassed.
- When `s.governor == nil`, the scheduler falls back cleanly to previous coarse counting behavior for backward compatibility.

### F. Per-Engine Limit Justifications
- **`ytdlp = 2`:** Conservative subprocess safety limit. Each `yt-dlp` invocation creates a process tree with FFmpeg children and high CPU/network utilization; running $\le 2$ avoids CPU starvation, thread exhaustion, and upstream rate-limiting/IP throttling.
- **`qbittorrent` and `aria2`:** External user-managed daemons. They default to being bounded directly by `GlobalTransferLimit` unless explicitly configured in `EngineLimits`.

### G. Dynamic Limit Lowering Semantics
- When the effective global transfer limit drops dynamically (e.g. from 5 to 2 while 3 downloads are active), existing leases are **preserved without killing or clamping running jobs**.
- Snapshot accurately reports 3 active transfers under limit 2 (`3/2`).
- `CanAdmit` and `TryAcquire` return `false`, blocking new admissions until active usage drops below the new limit.

### H. Startup Recovery Reconstruction Above Limits
- On restart, `Manager.recover()` reattaches running jobs. `ResourceGovernor.ReconstructJob(j)` reconstructs active jobs in `StatusDownloading` and `StatusProcessing` unconditionally.
- If recovered jobs exceed configured limits (e.g., limit lowered to 1 while 2 jobs were running), both jobs are tracked accurately (`2/1`) without rejection.
- Existing jobs continue running safely, while all new admissions are blocked until usage drops below capacity.

### I. Database Schema & State Integrity
- Zero schema migrations. No `wait_reason`, `permit`, or `semaphore` columns added to SQLite.
- All governor state remains purely in-memory and reconstructible on boot.
- All releases are idempotent and safe against double-release and underflow.
