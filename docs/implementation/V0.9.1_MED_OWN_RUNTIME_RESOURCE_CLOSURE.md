## 1. Scope Boundary

### Checkpoint 1 Scope (Implemented)
- **Engine availability:** `Engine.Available()` no longer executes yt-dlp. Availability is decided by `ToolManager.Resolve` (managed → configured → PATH, each verified by a version probe). `App.New` registers `ytdlp` only when `ToolInfo.Available()` is true **and** the resolved executable still exists on disk.
- **Durable media state machine:** `ANALYZING → AWAITING_SELECTION → QUEUED → DOWNLOADING → PROCESSING → COMPLETED / FAILED / CANCELLED`, with conditional (compare-and-set) persistence for both analysis completion and analysis failure.
- **Resource governance:** analysis and FFmpeg dimensions in `ResourceGovernor`, FIFO analysis admission (`WaitAcquireAnalysis`), owner-only analysis permit release (`ReleaseLease`), and conservative FFmpeg reservation for every yt-dlp media download.
- **yt-dlp usage coordination:** `UsageGate` provides shared use (downloads and analyses) and exclusive maintenance (`TryExclusive`, reserved for Checkpoint 2 activation).
- **Semantic routing:** known media hosts always classify as `ytdlp`, with no silent aria2 fallback. A missing engine produces a typed `YT_DLP_UNAVAILABLE` error (HTTP 409).
- **Media restart recovery:** recovery steps 2c and 2d resume or normalize interrupted analysis and preserve or truthfully fail awaiting-selection jobs.

### Checkpoint 2 Scope (Deferred, Not Implemented)
- Signed release asset verification (OpenPGP trust chain, `SHA2-256SUMS`).
- GitHub Releases acquisition and content-addressed staging cache.
- SQLite tool-records ledger, atomic activation, and last-known-good rollback.
- Authenticated managed-tool resolution.
- Settings UI Install / Update workflows.

No code for any Checkpoint 2 item exists in the working tree (verified in Section 6).

## 3. Defects Found and Corrected

### 3.1 Implementation pass

1. **Engine availability false positive.** `NewEngine` defaulted an empty path to `"yt-dlp"`, and `lifecycle.go` fell back to `cfg.YtdlpPath`, so a missing binary could register as a usable engine. Fixed by removing the default, adding a non-executing `Available()` check, and gating registration on `ytdlpInfo.Available() && ytdlpEng.Available()`. Test: `TestApp_YtdlpUnavailable_DeterministicVerification`.
2. **Probe launched for a job cancelled while queued.** The admitted worker now re-reads durable state after admission and exits without probing if the job is no longer `ANALYZING`. Test: `TestMediaAnalysis_CancelledWhileQueued_DoesNotExecute`.
3. **Lease identity.** Added `ReleaseLease(lease)` with pointer-identity checking, so an old worker cannot release a newer worker's lease. Test: `TestGovernor_ReleaseLease_PointerIdentity`.
4. **FFmpeg heuristic.** `RequiresFFmpeg` now returns true for every yt-dlp media job, and the scheduler reserves FFmpeg for media whenever the advisor or engine is absent.

### 3.3 G9: Cancel vs. SelectFormat (final race closure)

**Race analysis (pre-fix).** `SelectFormat` read the job, called `enqueueJob` (a separate `job_queue` upsert), and then wrote `status = queued` with an **unconditional** full-row `repo.Update` from its in-memory copy. `Cancel` read the job and also wrote `CANCELLED` with an unconditional full-row `Update`, followed by a separate `queueRepo.Delete`. The per-process `inFlightSelections` guard serialises selections against each other but does not order them against `Cancel`. Two concrete divergent outcomes were possible:

| Interleaving | Final state (pre-fix) |
|---|---|
| Selection enqueues → Cancel writes `CANCELLED` and deletes the entry → selection's `Update(queued)` lands | `queued` with **no** queue entry (status and queue diverge; job stranded) |
| Cancel writes `CANCELLED` → selection enqueues → selection's `Update(queued)` lands | `queued` **with** a runnable entry (cancellation lost; download would start) |

Both were reproduced on real SQLite. Temporarily reverting `SelectFormat` and `Cancel` to the pre-fix logic made `TestManager_SelectFormatVersusCancel_SQLite` fail with exactly these states (`status=queued entry=false` and `status=queued entry=true`). With the fix restored (verified by an identical file hash), it passes.

**Fix.** Two narrowly scoped transactional repository operations follow the existing `UpdateJobPriorityAndQueuePosition` job-plus-queue transaction precedent:

- `SQLiteJobRepository.SelectMediaFormat(jobID, info, entry)` runs in one transaction:
  1. `UPDATE jobs SET status='queued', media_info=? … WHERE id=? AND status='awaiting_selection'`. If zero rows are affected, it rolls back and returns `false`.
  2. Computes the queue position inside the transaction.
  3. Upserts the `job_queue` row.
  4. Commits.

  The status transition, the recorded format, and the queue entry become visible together or not at all.
- `SQLiteJobRepository.CancelAwaitingSelection(jobID)` runs in one transaction: `UPDATE jobs SET status='cancelled' … WHERE id=? AND status='awaiting_selection'`, then `DELETE FROM job_queue WHERE job_id=?`, then commit.
- `Manager.SelectFormat` validates as before, builds the selection on a **copy** of `MediaInfo` (the stored row is never mutated in place), and persists only through `SelectMediaFormat`. A lost compare-and-set returns `INVALID_JOB_STATE`. A transaction error returns `INTERNAL_ERROR` with nothing written. The separate `enqueueJob` call followed by an unconditional `Update` is gone.
- `Manager.Cancel`: when it observes `AWAITING_SELECTION`, it cancels through `CancelAwaitingSelection`. If that compare-and-set loses (because a selection committed first), it re-reads the job and re-evaluates from the authoritative state, which is then an ordinary `QUEUED` cancel that persists `CANCELLED` and deletes the queue entry. Re-evaluation is bounded (`maxCancelAttempts = 3`). Cancel paths for every other status are unchanged.

**Why this is atomic.** In SQLite, a transaction whose first statement is an `UPDATE` takes the write lock before reading the predicate. Both operations therefore serialise on the database write lock (`_busy_timeout=5000`), and each `WHERE … AND status='awaiting_selection'` predicate is evaluated under that lock. At most one of {selection, awaiting-selection cancel} can match the row. Because each operation writes its queue change in the same transaction as its status change, job status and queue membership cannot diverge. The in-memory guard remains as a fast-path de-duplicator, but single-winner selection no longer depends on it (`TestSelectCancel_RepositoryCASAdmitsSingleSelection`).

**Outcomes.**
- **Case A (cancel wins):** the job is `CANCELLED` and the selection compare-and-set loses. No selection is recorded, no queue row is written, and there is no dispatch and no engine `Start`.
- **Case B (selection wins):** the job is `QUEUED` with the selected format and its queue row committed together. The later `Cancel` sees `QUEUED` (directly, or after losing its compare-and-set) and persists `CANCELLED` while deleting the queue row.
- **Case C (failure):** a DB or queue-insert error rolls the whole transaction back, leaving `AWAITING_SELECTION` with no selection, no queue row, and the guard released. A later `Cancel` still succeeds. A failed cancel transaction leaves the job uncancelled, publishes no event, and can be retried.

## 4. Invariant Verification

### A. Engine availability

```text
ToolManager.Resolve("yt-dlp")     managed → configured (non-default) → PATH; each needs a successful --version probe
        │
        ▼
ToolInfo.Available()              Status == active && VerificationStatus == verified
        │
        ▼
App.New                           resolvedYtdlpPath = "" unless Available()
        │
        ▼
ytdlp.NewEngine(path, ffmpeg)     no default "yt-dlp" string
        │
        ▼
Engine.Available()                non-executing: os.Stat (paths) / exec.LookPath (bare names); "" → false
        │
        ▼
Registry.Register("ytdlp")        only if ToolInfo.Available() && Engine.Available()
```

- A non-empty configured path or the bare string `"yt-dlp"` is never treated as proof of availability. `ToolManager` decides.
- Configured and system fallbacks still work, because `ToolManager` resolves them and returns the absolute path.
- `CreateWithOptions` re-checks registration and `Available()` per request, so a binary deleted at runtime is refused.
- `TestApp_YtdlpUnavailable_DeterministicVerification` (empty PATH, nonexistent configured path, isolated data dir): the tool is unavailable, `ytdlp` is not registered, a YouTube URL returns `YT_DLP_UNAVAILABLE`, and 0 jobs are persisted (so no media job and no aria2 job or queue entry).

### B. Analysis and cancellation

**Conditional metadata persistence.** `CompleteMediaAnalysis` writes status, metadata, and name in one `UPDATE … WHERE id = ? AND status = 'analyzing'`. Zero rows affected returns `won = false`, and the worker logs and returns with no event. On success, the event carries the re-read authoritative job. A persistence error emits no event. `FailMediaAnalysis` gives the failure side the same guarantee.

**Ownership lifecycle.**

```text
CreateWithOptions / Retry / dispatchPendingMediaAnalyses
  → analyzeMedia: registerAnalysisWorker (refuses duplicate JobID; handle-owned)
  → WaitAcquireAnalysis (FIFO; ctx cancel removes waiter; shutdown → ErrGovernorClosed → job left ANALYZING)
  → re-read durable state; not ANALYZING → ReleaseLease + exit, no probe
  → execCtx = WithTimeout(ctx, 180s)        (deadline starts after admission)
  → AnalyzeWithPolicy: UsageGate.AcquireUse → exec.CommandContext(...).Output() → defer release
  → ReleaseLease(analysisLease)            (only after the analyzer returned, i.e. the probe has exited)
  → CompleteMediaAnalysis / FailMediaAnalysis (compare-and-set)
  → unregisterAnalysisWorker(handle)
```

- `Cancel` signals the worker context and persists `CANCELLED`. `removeActive` → `ReleaseTransfer` leaves the analysis permit alone, and the worker frees it once the probe terminates (G1).
- The cancelled worker stays registered until it exits, so `Retry` and recovery dispatch cannot start a second probe for the same JobID (G2).
- `Manager.Stop` cancels every registered analysis worker. `gov.Stop` wakes all parked waiters.
- The permit cannot leak: the release is deferred, and `ReleaseLease` is identity-checked and idempotent.

**FIFO admission.** Immediate admission happens only when the queue is empty and capacity is free, all under one mutex, so the capacity check is atomic. Releases hand slots to waiters in queue order inside `releaseLocked`. A cancelled waiter is removed under the lock. If admission and cancellation race, the exact admitted lease is released. Waiters block on per-waiter channels, so there is no polling. Every wakeup happens under the lock that mutates the queue, so no wakeup is lost. The contention test confirms no leftover waiters or permits after 1,600 racing acquisitions.

**Retry and SelectFormat.**
- `Retry` rejects `ANALYZING`, any job with a live analysis worker, and `AWAITING_SELECTION` (no needless re-analysis). Retry of a failed media job still re-enters `ANALYZING` (`TestMediaState_RetryPolicy`).
- `SelectFormat` requires `AWAITING_SELECTION` and non-nil `MediaInfo`. An in-process per-job guard admits one selector at a time and is released via `defer` on every path. The concurrent test shows exactly one success across 8 racers × 50 rounds.
- Selection persistence is a single conditional transaction (`SelectMediaFormat`: status compare-and-set + queue row). A failure leaves no half-selected job and no queue row. See G9 (Section 3.3).

### C. Governor and scheduler

- **API compatibility:** `TryAcquire`, `Release`, `GetLease`, and `ReconstructJob` keep their signatures and semantics. An equivalent request is idempotent. Different requirements for a held JobID return `ErrLeaseConflict`. `ReleaseLease` and `ReleaseTransfer` are additive.
- **Accounting:**

  | Lease | Analysis | Global transfer | Engine (ytdlp) | FFmpeg |
  |---|---|---|---|---|
  | Media analysis | 1 | 0 | 0 | 0 |
  | yt-dlp media download | 0 | 1 | 1 | 1 |
  | aria2 / qB transfer | 0 | 1 | 1 (per engine) | 0 |

  Release decrements only the flags recorded on the lease. A failed compound admission increments nothing, because every check happens before any counter changes. Double release is a no-op, and counters are clamped at zero.
- **Analysis → download:** the analysis lease is released before `CompleteMediaAnalysis` makes `AWAITING_SELECTION` visible, so a later scheduler `TryAcquire` never hits a spurious `ErrLeaseConflict`. Failed or cancelled analyses release via the deferred owner release, so no stale lease remains.
- **FFmpeg:** yt-dlp may invoke FFmpeg for merge, remux, fixups, and subtitle embedding or conversion, and no tested no-FFmpeg profile exists. So `RequiresFFmpeg` reserves the permit for every media download. The scheduler also reserves it when the engine is missing or does not implement the advisor. The advisor interface has no error return, so there is no error branch that could skip admission.
- **Scheduler / Run Now:** every governor-mode dispatch passes `TryAcquire` with the full requirements before `dispatchSingle`. Run Now only moves the queue position (`TestSchedulerGovernor_RunNowRespectsHardResourceLimit`). Failed in-flight reservation and failed dispatch release the lease. `PROCESSING` keeps its lease until the terminal transition.
- **Recovery:** `StartBackgroundTasks` runs `recover` first, then calls `ReconstructJob` only for jobs in `activeJobs`, then dispatches pending media analyses. As a result, interrupted media downloads become `FAILED` with no phantom lease, `AWAITING_SELECTION` and `QUEUED` media hold no lease, and resumed analyses acquire a fresh permit through FIFO admission. `RestartedMetadataAcquisitions` is incremented only when an analysis restart is actually scheduled, mirroring the existing torrent path.

### D. UsageGate

- Shared use counts and exclusive mode are mutated under one mutex, so there is no check-then-act race. `AcquireUse` fails during exclusive mode. `TryExclusive` fails while uses are active or exclusive mode is already held. Releases are wrapped in `sync.Once`, so they are idempotent.
- No lock is held across subprocess execution. The gate mutex is a leaf lock and never calls into Manager, engine, or ToolManager, so it cannot take part in a lock-order cycle.
- **`Engine.Start`** acquires use synchronously before any goroutine handoff. Auth-preparation and subtitle-validation failures release before returning. `runDownload` releases via `defer` after `proc.Wait()` (supervised tree) or after a pipe or `StartOwned` failure, so there is no early or double release.
- **Analysis** acquires before building the command and releases via `defer` after `cmd.Output()` returns.
- **Exec audit:** the only yt-dlp executions in `internal/engine/ytdlp` are `runDownload` (`StartOwned`) and `AnalyzeWithPolicy` (`CommandContext`), and both are gated. ToolManager's `--version` probe is the preserved FND-4B short-probe exemption.

### E. Routing and compatibility

- `Registry.Detect` matches exact or dot-suffixed hosts. `youtube.com.attacker.com`, `fakeyoutube.com`, and `notvimeo.com` route to aria2. Known media hosts route to `ytdlp` whether or not the engine is registered.
- Missing or unavailable yt-dlp returns `YT_DLP_UNAVAILABLE` from the shared `Manager`. HTTP maps it to 409, and the Wails transport receives the same `*AppError` code from the same `Manager` call.
- The diff does not touch TOR-EXT qB ownership, protected credentials, external aria2 ownership, RecoverySummary schema, FinalizationJournal, StateSync, the support-bundle schema, desktop IPC, or no-localhost mode.
