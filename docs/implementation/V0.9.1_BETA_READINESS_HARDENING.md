## 3. A — WebView2 detection and failure UX

**Official guidance (verified 2026-11-13).** Microsoft Learn, *Distribute your app and the WebView2 Runtime* (page updated 2026-10-02), "Detect if a WebView2 Runtime is already installed":

- inspect `pv (REG_SZ)` under `HKLM\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}` (64-bit Windows) or `HKLM\SOFTWARE\Microsoft\EdgeUpdate\Clients\{…}` (32-bit Windows), and `HKCU\Software\Microsoft\EdgeUpdate\Clients\{…}`;
- installed if at least one of these is present with a version greater than 0.0.0.0;
- `null`, empty or `0.0.0.0` means not installed.

**Defect (VS).** The installer read `EdgeUpdate\ClientState\{…}` value `EBWebView` and Uninstall entries (not the documented location). It also claimed a minimum version (86.0.616.0) that it never checked. The application itself had no check at all. In Wails v3.0.0-beta.23, `setupChromium` logs "error getting WebView2 version" and returns, so on a machine without the Runtime the tray and full background runtime would start and look healthy while no window could ever appear.

**Fix:**

- **Installer** (`CheckWebView2`): reads `pv` under `SOFTWARE\Microsoft\EdgeUpdate\Clients\{…}` in HKLM through `SetRegView 32` (which resolves to WOW6432Node on 64-bit Windows and to the native key on 32-bit Windows, exactly the two documented paths), then HKCU. It rejects empty and `0.0.0.0`. The message no longer asserts a minimum version. Per-user installation (`RequestExecutionLevel user`) is unchanged, and no bootstrapper was added.
- **Desktop host:**
  - `detectWebView2` reads the same two documented locations (`registry.WOW64_32KEY` for HKLM) and applies the same rule. It also rejects non-numeric values.
  - `webView2StartupDecision` runs in `main` **after** single-instance establishment (second launches are still forwarded) and **before** `startDesktopCore`.
  - If the Runtime is missing, a native message box explains what is needed and where to get it. The process exits with code 1 *before* any core, database, tray or worker starts, so no headless runtime can appear healthy.
  - No minimum version is asserted.

**Tests (VT):**

- `TestValidWebView2Version` (including `0.0.0.0`, empty, garbage, overflow).
- `TestEvaluateWebView2_MicrosoftRule` (eight location combinations).
- `TestWebView2StartupDecision` (message content, no version claim).
- `TestReadWebView2Probe_RegistryValue`: real registry reads against a throwaway HKCU test key, deleted afterwards.
- `TestDetectWebView2_ThisMachine`: this machine reports `installed=true version=157.0.4341.46 scope=per-machine`.
- `TestInstallerWebView2Detection_MatchesDocumentedRule`: static check of the NSIS function. Run against the committed (pre-fix) script it fails all **7** assertions.

**Not tested (NT):** a real machine *without* WebView2 (needs a clean VM), and the installer itself (not rebuilt by instruction).

## 5. C — Shutdown correction

**Confirmed unsafe behaviour (VS):**

- `App.Shutdown` called `manager.Stop()` without honouring its context.
- `Manager.Stop` waits on the scheduler and monitor wait-groups, so a dispatch blocked in an engine call (or a monitor tick blocked in a status call) blocked Quit **indefinitely**. Reverting the fix makes the stuck-worker test hang until the 45 s test timeout (VT).
- Any concurrent second `Shutdown` inherited that unbounded wait.
- `Monitor.Stop` panicked on a second call.

**Bounded contract (`internal/app/lifecycle.go`):**

1. Tracker drain: bounded by ctx (unchanged).
2. **Manager stop: bounded by ctx.** A worker that does not exit is abandoned and `ErrShutdownIncomplete` is returned; it is never waited for indefinitely.
3. **Process supervisor: always runs.** If ctx is already exhausted it gets its own bounded grace (`shutdownCleanupGrace` = 3 s), so owned process trees (Job Objects) are still terminated.
4. Database close: always runs. In-flight statements finish first. An abandoned worker's later writes fail against the closed handle instead of racing a successor runtime, and durable recovery reconciles on the next start.
5. Ownership locks are released after the database is closed.

Concurrent callers keep the **established join contract**: they never return while the shared teardown is still running, because the database and ownership locks are still held. That is asserted by the pre-existing `TestApp_Shutdown_Concurrent_Join_IgnoresContextCancellation`. Their wait is now bounded too, because the owner's teardown is bounded by the owner's deadline plus the cleanup grace. An intermediate version of this change let joiners return on their own deadline. The full suite caught that against the existing test, so it was reverted rather than weakening the test. Repeated calls return the recorded outcome without a second pass. There is no `os.Exit`; the desktop exits normally after `wailsApp.Run` returns.

**Guarantees:**

- Preserved: process-tree termination, database closure and ordered lock release.
- Not preserved for an abandoned worker: its in-memory step (for example a job state write) may be lost. Startup recovery handles that state as after a crash.

**Tests (VT):**

- `TestShutdown_NormalCompletesWithinDeadline`
- `TestShutdown_WorkersAlreadyStopped`
- `TestShutdown_StuckWorkerIsBounded`: returns `ErrShutdownIncomplete` within deadline + grace; an owned child process is terminated; the database is closed; a relaunch on the same database starts and stops cleanly.
- `TestShutdown_ConcurrentAndRepeatedRequests`: with a stuck worker, the owner returns within its deadline + grace; the joiner returns only after the owner, with the same `ErrShutdownIncomplete` outcome; a later call returns the recorded outcome; worker stop runs exactly once.
- All 7 pre-existing `TestApp_Shutdown*` tests still pass, unchanged.
- `TestDesktopCoreCloseToTrayThenQuitThenRelaunch`: real `DesktopLifecycle`: hide keeps workers alive, Quit stops them, a repeated Quit is ignored, relaunch works.

These are harness tests; no GUI was exercised.

## 7. E — CI and race-detection readiness

**Why `dev` was not validated (VS/VT):**

- The workflow triggers only on `main` and three v0.7 feature branches.
- Its last `main` run (v0.9 chore) failed at **gofmt**, so tests and `-race` never ran there either.
- The backend job used `ubuntu-latest`, where `cmd/desktop` (Wails' Linux backend needs cgo plus GTK/WebKit) cannot build. The Windows-only Job Object tests would not run there either.

**Change (`.github/workflows/ci.yml`):**

- Triggers on push and pull requests for `dev`, in addition to the existing branches.
- Explicit `permissions: contents: read`, a tightening; there are no other workflows and no packaging, signing or publication steps.
- The backend job moves to `windows-latest` (shell bash). It:
  - disables autocrlf so gofmt sees repository LF;
  - takes the Go version from `go.mod`;
  - runs the gofmt check, `go vet`, the server build, `go test ./...`, a printout of the C toolchain, and `go test -race ./...` (`CGO_ENABLED=1`, 30 min timeout).
- The frontend job is unchanged.
- The five committed-but-unformatted files were gofmt'd (whitespace only), so the gofmt gate can pass.

**Race detector:** **NOT RUN — LOCAL CGO LIMITATION.** No CI run exists for this change yet, because it is uncommitted. The next Git checkpoint pushed to `dev` will trigger the workflow; its `-race` step (with the printed `gcc --version`) supplies the first actual race evidence. If the Windows runner lacks a usable C toolchain, that step fails visibly rather than being skipped. Deterministic interleaving tests are not a substitute for `go test -race`.

## 8. F — Default download location (owner decision; not changed)

- **Current behaviour (VS):** the desktop host sets `DownloadDir = %APPDATA%\GoDownloader\downloads`, which is the **Roaming** profile. DSK-4E deliberately anchors data there and preserves it on uninstall. The settings service overrides it only when the user chose a directory.
- **Risk:** on domain/roaming profiles, multi-GB downloads would sync at logon/logoff; on home machines the effect is only an unusual location.
- **Roadmap:** no roadmap item requires changing the default for V0.9.1, so this round makes no change.
- **Recommendation for owner approval:**
  - New installs default to the user's **Downloads** known folder (`FOLDERID_Downloads`) `\GoDownloader`.
  - Existing installs keep `%APPDATA%\GoDownloader\downloads` when that folder exists or settings already resolve to it. Explicit user choices are never changed.
  - No files are moved or deleted.
  - Database and data stay under `%APPDATA%\GoDownloader` (outside the install directory).
  - This needs settings-migration tests with an upgrade fixture before release.

## 11. Governance packet — SPK-SYN3-07 (Process-tree ownership)

**Status: PENDING OWNER ACCEPTANCE.** This packet does not approve the gate.

1. **Required invariant** (ROADMAP line 134, V0.9.1 gate at line 294): GoDownloader may claim ownership of the processes it starts only if every child and grandchild is contained, and is terminated on cancel, timeout and application shutdown, without affecting processes it does not own.
2. **Implementation evidence (VS):**
   - FND-4B ([V0.8.0_FND4B_PROCESS_SUPERVISOR.md](V0.8.0_FND4B_PROCESS_SUPERVISOR.md)): processes are created suspended, assigned to a Job Object with `KILL_ON_JOB_CLOSE`, containment is verified, then they resume; a single context watcher; idempotent terminate/wait.
   - H-2 ([V0.9.1_RUNTIME_BLOCKER_CORRECTIONS.md](V0.9.1_RUNTIME_BLOCKER_CORRECTIONS.md) §14): media analysis also runs supervised, and teardown waits until every **job member** is gone. There is no global scan and no name-based kill.
   - This round: shutdown always runs process-tree cleanup, even after its deadline (Section 5).
3. **Automated test evidence (VT):**
   - `internal/process` suite;
   - 6 helper-tree analysis tests (cancel, deadline, graceful exit with lingering child, failed exit, failed creation, supervisor shutdown);
   - `TestShutdown_StuckWorkerIsBounded` (an owned child is terminated by a bounded shutdown).
4. **Real Windows process evidence (VT):** the official PyInstaller `yt-dlp.exe` 2026.10.26 (SHA-256 pinned, `f5389d36…7a7d`) root plus child, observed and confirmed dead after cancel, deadline, natural exit and supervisor shutdown (corrections report §15 and §28, ×2 repeat runs).
5. **Remaining limitations:**
   - Unix process-group teardown is not re-verified for V0.9.1 (Windows-only target).
   - FFmpeg runs inside yt-dlp's tree; there is no separate GoDownloader-owned FFmpeg path.
   - No race-detector run yet (Section 7).
   - No packaged-GUI Quit test.
   - External daemons (aria2, qBittorrent) are **not** owned processes (TOR-EXT boundary), and are out of scope by design.
6. **Recommended disposition:** accept SPK-SYN3-07 for **Windows V0.9.1 Beta**, conditional on the first CI `-race` run passing on `dev`. Record the Unix and packaged-GUI checks as V0.9.2 RC items.

## 12. Governance packet — Managed yt-dlp inventory/provenance

**Status: PENDING OWNER ACCEPTANCE.** Technical recommendation only; not legal approval; managed activation is not approved here.

1. **Acquisition policy:**
   - Only on explicit user action (Install/Update), Windows amd64 only.
   - Latest **stable** release from `api.github.com/repos/yt-dlp/yt-dlp/releases/latest`; drafts and prereleases are refused.
   - The assets `yt-dlp.exe`, `SHA2-256SUMS` and `SHA2-256SUMS.sig` must each appear exactly once.
   - HTTPS with an exact host allowlist (`api.github.com`, `release-assets.githubusercontent.com`), at most 3 redirects, credential headers stripped, size and time bounded, no retries.
   - Downgrades are refused.
2. **Pinned signing key:** yt-dlp `public.key`, fingerprint `AC0CBBE6848D6A873464AF4E57CF65933B5A7581` (identity Simon Sawicki), embedded at build time. There is no network key fetch, no TOFU and no rotation. The youtube-dl key is explicitly not trusted.
3. **Trust chain:** detached OpenPGP signature over `SHA2-256SUMS`, verified with the pinned key (go-crypto; RSA ≥ 3072, SHA-256/384/512 only) → strict manifest parse → exact `yt-dlp.exe` digest → streamed hash plus re-hash from disk → only then a bounded `--version` probe matching the tag → immutable content-addressed promotion. Nothing executes before the digest matches.
4. **Ownership:**
   - `managed` (authenticated ledger), `legacy_managed_directory` (version-probed only), `user_configured`, `system_path`.
   - Only the ledger can mark a binary authenticated; generic observations cannot.
5. **Active/LKG SQLite provenance:**
   - `managed_tool_ledger(name, sha256, version, release_tag, file_name, signer_fingerprint, status, authenticated_at, …)`.
   - Partial unique indexes enforce at most one `active` and one `last_known_good` row.
   - Activation is a single transaction with a compare-and-set on the previous active row.
   - Startup re-hashes the active binary before use.
6. **Runtime acquisition vs redistribution:** GoDownloader does **not** ship yt-dlp. The installer payload contains only `GoDownloader.exe` (Section 13). The user's machine downloads the official binary directly from upstream.
7. **GPLv3+ caveat:** the yt-dlp *source* is Unlicense, but the official Windows `yt-dlp.exe` is a PyInstaller bundle containing GPLv3+ components, so the standalone executable is a GPLv3+ combined work (plus e.g. certifi MPL-2.0, mutagen GPLv2+). GoDownloader runs it as a separate process and does not link it. Whether runtime acquisition needs a user-facing disclosure is an owner/legal question.
8. **Remaining threats:**
   - A *replayed old signed release* on first install (anti-downgrade protects existing installs only).
   - A same-user process replacing the store file between hash and execution (outside the threat model: such an attacker already controls the user's executables).
9. **Inventory: shipped vs runtime-acquired:**
   - Shipped: `GoDownloader.exe` only.
   - Runtime-acquired on user action: `yt-dlp.exe`.
   - External, user-managed: FFmpeg, FFprobe, Deno, aria2, qBittorrent.
   - Provided by the OS / Microsoft: the WebView2 Runtime.
10. **Recommended private-Beta policy:**
    - Allow managed yt-dlp activation for the **private** Beta under the current trust chain.
    - Show (or document in Beta notes) that yt-dlp is downloaded from the official GitHub releases, is GPLv3+ as distributed, and is not bundled.
    - Keep public distribution blocked until P-1 is resolved.

### 19.7 Shutdown ownership and abandoned-worker safety

The contract after this gate:

1. **Signal every worker (non-blocking).** The scheduler and reconciler contexts are cancelled, the monitor is stopped, the governor is closed and active/analysis tasks are cancelled.
2. **Bounded wait** (ctx, or grace if ctx is already spent).
3. **Supervisor shutdown, always.** It terminates owned Job Object trees, and `StartOwned` refuses new processes from then on.
4. **Database close.** New statements fail with an error, not a panic.
5. **Lock release.**

The join contract is preserved: the pre-existing `TestApp_Shutdown_Concurrent_Join_IgnoresContextCancellation` still passes. Repeated calls are idempotent, and the error is the truthful `ErrShutdownIncomplete`.

**Remaining limits:**

- A worker stuck *inside* an external call is not interrupted. Only its wait is abandoned.
- An abandoned dispatch can still reach the external aria2 or qBittorrent daemon (#14).
- A statement it had already started may complete after Close (#13).

In the hosts, the process exits right after Shutdown, which ends any remaining goroutine. A successor runtime in the **same** process is not a production scenario.
