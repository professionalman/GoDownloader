### 3. Binding & Exposure Analysis

* **Default Binding:**
  * Configured via `internal/config/config.go`: `getEnv("LISTEN_ADDR", "127.0.0.1:8080")`.
  * The production server binds exclusively to the local IPv4 loopback interface (`127.0.0.1`).
* **Fail-Closed Non-Loopback Policy (`CheckNonLoopbackBind`):**
  * When `LISTEN_ADDR` specifies a non-loopback address (such as `0.0.0.0`, an external LAN IP, or empty host `:8080`), `api.CheckNonLoopbackBind` verifies the `GODOWNLOADER_ALLOW_NON_LOOPBACK` environment variable.
  * If `GODOWNLOADER_ALLOW_NON_LOOPBACK != "1"`, the server refuses to start and fails closed with:
    `binding to non-loopback address forbidden without GODOWNLOADER_ALLOW_NON_LOOPBACK=1`.
* **Logging:**
  * Server startup logs `http://<listen_addr>`. No secrets, tokens, or credential strings are output.

### 4. Threat Model & Defense Invariants

#### 4.1 Core Security Invariant
An arbitrary untrusted website visited in the user's browser must not be able to read or mutate GoDownloader's local application state merely because GoDownloader is running on localhost. REST/SSE surfaces that expose application state must have an explicit, verified trust boundary.

#### 4.2 Threat Analysis & Countermeasures Matrix

| Threat ID | Threat Vector | Attack Scenario | Defense Mechanism | Result |
| :--- | :--- | :--- | :--- | :--- |

| **B** | Cross-site form/fetch against mutating APIs (CSRF) | `https://evil.com` embeds `<form method="POST" action="http://localhost:8080/api/v1/jobs">` | 1. `SameSite=Strict` session cookie omitted by browser. 2. Cross-origin `Origin` header rejected. 3. HTML forms cannot set `X-CSRF-Token` header. | **BLOCKED (401 / 403)** |
| **C** | Cross-origin read of local state | `https://evil.com` attempts cross-origin fetch of `/sync/snapshot` or `/settings` | 1. CORS does not allow `evil.com`. 2. Origin check rejects with 403. 3. Missing session cookie returns 401. | **BLOCKED (401 / 403)** |
| **D** | Hostile or spoofed Origin headers | Attacker page sends misleading Origin headers | Origin strings must exactly match loopback patterns (`http://localhost:*`, `http://127.0.0.1:*`, `http://[::1]:*`) or explicit dev origins. | **BLOCKED (403)** |
| **E** | Permissive CORS wildcard | Server accidentally sending `Access-Control-Allow-Origin: *` | CORS `AllowOriginFunc` strictly validates against loopback map. Wildcard `*` is never emitted. | **BLOCKED** |
| **F** | Private Network Access (PNA) preflight | Attacker triggers Chrome/Edge PNA preflight to localhost | Preflight from non-loopback origins never receives `Access-Control-Allow-Private-Network: true`. | **BLOCKED** |
| **G** | DNS Rebinding | Attacker points `rebind.evil.com` to `127.0.0.1`; browser sends `Host: rebind.evil.com:8080` | `ValidateHost` verifies `r.Host` matches loopback hostnames (`localhost`, `127.0.0.1`, `[::1]`). Hostile hostnames are rejected with 403. | **BLOCKED (403)** |
| **H** | Credential leakage through URLs & logs | Session tokens leaking in query strings, access logs, or history | Zero session credentials accepted in URL query parameters. SSE uses same-origin cookies. Query tokens ignored. | **PROTECTED** |

| **J** | Browser reload / reconnect | User reloads browser tab or opens multiple tabs | Session cookies (`godownloader_session`, `godownloader_csrf`) persist across page loads and tabs. Reconnect is seamless. | **VERIFIED** |
| **K** | Frontend development mode | Vite frontend running on `http://localhost:5173` | Vite dev proxy routes `/api` to `localhost:8080`. Allowed origins explicitly permit `http://localhost:5173`. | **SUPPORTED** |
| **L** | Accidental non-loopback binding | User/script configures `LISTEN_ADDR=0.0.0.0:8080` | `CheckNonLoopbackBind` fails closed unless `GODOWNLOADER_ALLOW_NON_LOOPBACK=1` is explicitly set. | **FAIL-CLOSED** |

#### 5.1 SecurityManager (`internal/api/security.go`)
* **Tokens:**
  * `sessionToken`: 32 cryptographically secure random bytes (hex-encoded) generated at process startup.
  * `csrfToken`: 32 cryptographically secure random bytes (hex-encoded) generated at process startup.
* **Cookies:**
  * `godownloader_session`: `HttpOnly; SameSite=Strict; Path=/`.
  * `godownloader_csrf`: `SameSite=Strict; Path=/` (readable by client JavaScript).
* **Double-Submit / Header CSRF:**
  * State-changing requests (`POST`, `PUT`, `DELETE`) require the `X-CSRF-Token` header matching `csrfToken`.
  * HTML forms cannot attach custom headers, preventing ambient authority CSRF.
* **Host Header Validation:**
  * Strips port and compares against allowed loopback hosts (`localhost`, `127.0.0.1`, `[::1]`, and loopback net block `127.0.0.0/8`).
  * Defeats DNS rebinding before any route handler executes.
* **Zero Secrets in URLs:**
  * `ValidateSession` only checks `Cookie`, `Authorization: Bearer`, and `X-Session-Token`.
  * `r.URL.Query().Get("token")` is deliberately unsupported and rejected.

#### 5.2 Frontend Client (`web/src/api.ts` & `web/src/App.tsx`)
* **`initSession()`:** Performs handshake with `GET /api/v1/auth/session` on app bootstrap and caches the CSRF token.
* **`authFetch(url, init)`:**
  * Attaches `credentials: 'same-origin'` to all requests.
  * Automatically injects `X-CSRF-Token` on mutating requests (`POST`, `PUT`, `DELETE`).
* **`connectSSE()`:**
  * Opens native `EventSource` to same-origin `${API_BASE}/events`.
  * Browser automatically transmits the `godownloader_session` cookie.
  * URL query string contains only `?cursor=<seq>`, with zero tokens or secrets.

## 7. Final Bootstrap & Production Trust Boundary Verification

### 7.1 Previous vs Final Bootstrap Behavior
- **Previous Behavior:**
  `GET /api/v1/auth/session` set `godownloader_session` and `godownloader_csrf` cookies, but ALSO returned `token: sm.sessionToken` in the JSON response body.
  Additionally, `spaHandler` unconditionally called `SetSessionCookies` on `/` or `/index.html`.
- **Final Behavior:**
  `GET /api/v1/auth/session` is the single canonical bootstrap endpoint. It issues `godownloader_session` and `godownloader_csrf` cookies via HTTP headers and returns ONLY:
  ```json
  {
    "status": "ok",
    "csrfToken": "<csrf_token>"
  }
  ```
  Root page (`/`, `/index.html`) cookie issuance was removed under YAGNI to eliminate competing bootstrap paths and keep static asset delivery cleanly separated from session state.

### 7.2 Session Secret Visibility in JavaScript
- **Result:** **STRICTLY NOT VISIBLE.**
  The raw `sessionToken` is never transmitted in JSON response bodies, URL query strings, or client-accessible cookies. It is strictly confined to the `HttpOnly; SameSite=Strict` cookie, preserving the browser security boundary against script inspection or XSS exfiltration.

### 7.3 Bearer Token Support Decision
- **Decision:** **REMOVED / DEFERRED under Ponytail / YAGNI.**
  An exhaustive audit of the codebase confirmed that GoDownloader is a local, single-user application with zero external or non-browser API clients.
  Offering `Authorization: Bearer` or `X-Session-Token` would require distributing the raw bearer secret or creating an arbitrary token distribution surface.
  Eliminating Bearer tokens enforces an invariant: all browser interactions rely strictly on `HttpOnly; SameSite=Strict` cookies.

### 7.4 Root-Page Session Cookie Decision
- **Decision:** **REMOVED from `spaHandler`.**
  Setting cookies during static HTML delivery was redundant with `initSession()` (`GET /api/v1/auth/session`), which runs deterministically during frontend mounting. Removing it prevents unintended cookie modification on static reload or navigation.

### 7.5 Production vs Development Origin Policy
- **Production Policy (`GODOWNLOADER_DEV_MODE=""` or `false`):**
  Only the exact loopback origins on the configured listen port are trusted (`http://localhost:8080`, `http://127.0.0.1:8080`, `http://[::1]:8080`).
  Development origins such as `http://localhost:5173` are **REJECTED with HTTP 403 Forbidden**. Arbitrary local ports (e.g. `9999`, `3000`) are rejected.
- **Development Policy (`GODOWNLOADER_DEV_MODE=1` or `true`):**
  Explicitly permits Vite development server origins (`http://localhost:5173`, `http://127.0.0.1:5173`, `http://[::1]:5173`).

### 7.6 Vite Development Flow Verification
- `vite.config.ts` configures a dev proxy for `/api` pointing to `http://localhost:8080` with `changeOrigin: true`.
- Browser fetch requests from `http://localhost:5173` to `/api/v1/...` are same-origin to Vite, which proxies headers (including `Cookie` and `X-CSRF-Token`) directly to the backend.
- `credentials: 'same-origin'` works seamlessly because the browser communicates with `localhost:5173`.
- Production builds (`dist/`) run directly on the backend's static file server on port 8080 where requests are genuinely same-origin.

### 7.7 Non-Loopback Final Policy & Unauthenticated LAN Risk
- **Policy:** **UNCONDITIONAL REJECTION.**
  The unsafe override `GODOWNLOADER_ALLOW_NON_LOOPBACK` was completely removed.
  `CheckNonLoopbackBind` unconditionally fails if `LISTEN_ADDR` resolves to `0.0.0.0`, an external LAN IP, or an empty host (`:8080`).
- **LAN Security Invariant:**
  Because raw HTTP clients (curl, scripts, remote machines) control their own `Host` headers, Host validation cannot authenticate raw clients on a local area network. Binding to non-loopback would expose an unauthenticated LAN API. Enforcing loopback-only binding eliminates this vulnerability completely without scope creep.

### 7.8 Host-Validation Boundary Clarification
- Global `ValidateHost` middleware protects against **DNS rebinding** attacks from web browsers (rejecting malicious external domains mapped to `127.0.0.1`).
- Host validation is explicitly documented as a browser defense, **NOT** as a general client authentication mechanism.

### 7.9 Cookie Properties
- `godownloader_session`:
  - `Name`: `godownloader_session`
  - `Value`: 32-byte hex cryptographic random string
  - `Path`: `/`
  - `HttpOnly`: `true`
  - `SameSite`: `http.SameSiteStrictMode`
  - `Secure`: `false` (plain HTTP loopback; transport never leaves local kernel loopback)
  - `MaxAge`: 0 (browser session duration)
- `godownloader_csrf`:
  - `Name`: `godownloader_csrf`
  - `Value`: 32-byte hex cryptographic random string
  - `Path`: `/`
  - `HttpOnly`: `false` (accessible to client JavaScript for `X-CSRF-Token` header)
  - `SameSite`: `http.SameSiteStrictMode`
  - `Secure`: `false`
  - `MaxAge`: 0 (browser session duration)

### 7.10 Backend Restart & Session Lifecycle
- When the backend restarts, a new ephemeral session secret is generated.
- Stale session cookies from previous runs return `401 Unauthorized`.
- `authFetch` in the frontend intercepts 401 responses, performs a single re-bootstrap via `initSession()`, updates the CSRF token and session cookies, and retries the original request.
- If the retry fails with 401 again, it does not retry further, preventing infinite loops.
- Both backend test (`TestSecurity_BackendRestartStaleCookieRecovers`) and frontend test (`401 session expiry/restart triggers single re-bootstrap and succeeds on retry`) verify this recovery flow deterministically.

## 8. Final Runtime Session Recovery & Security Scope Verification

### 8.1 SSE Restart Behavior Before Review
- **Trace Analysis:**
  Prior to this review, when backend instance A stopped and backend instance B started with a new ephemeral session token, the browser still held instance A's stale `godownloader_session` cookie.
  `EventSource` attempted to connect to `/api/v1/events` on backend B. Backend B returned `401 Unauthorized`.
  In `App.tsx`, `handleError` only updated UI state (`setConnectionState('reconnecting')`). It did NOT trigger re-authentication or snapshot rehydration.
  Because no REST request was made, the `authFetch` 401 recovery interceptor was never invoked.
  The connection remained stuck indefinitely or continuously attempted to reconnect with the same stale cookie.

### 8.2 Final Restart / Rebootstrap Behavior & Convergence
- **Smallest Architectural Correction:**
  Updated `handleError` in `App.tsx`:
  ```tsx
  const handleError = () => {
    setConnectionState('reconnecting');
    if (activeEsRef.current === es) {
      handleSyncRequired();
    }
  };
  ```
  And in `useEffect` cleanup, guarded `es.close()` to ensure idempotency.
- **Convergence Lifecycle:**
  1. `EventSource` encounters an error (e.g. 401 from backend restart).
  2. `handleError` runs: immediately closes and nullifies `activeEsRef.current` (preventing any stale connection or loop).
  3. `handleSyncRequired` requests `getSyncSnapshot()`.
  4. `authFetch` sends `GET /api/v1/sync/snapshot`, receives 401 due to the stale cookie.
  5. `authFetch` calls `initSession()` (`GET /api/v1/auth/session`), which receives a fresh `godownloader_session` cookie and updates `csrfToken`.
  6. `authFetch` retries `getSyncSnapshot()` with the new session, which succeeds (200 OK).
  7. State is reconciled, and authoritative snapshot cursor $C$ is installed (`lastAppliedCursorRef.current = snapshot.cursor`).
  8. `streamTrigger` increments, triggering `useEffect` to open a brand-new `EventSource` initialized from cursor $C$.
  9. The new `EventSource` connects with the new cookie, `open` fires, and state becomes `connected`.
  10. Zero stale streams remain active.

### 8.3 Frontend Bounded Retry Behavior
- `authFetch` guards retry with `isRetry: true`. If re-bootstrap itself fails or if the retried request returns 401 again, it does NOT retry further, preventing infinite loops.
- `handleSyncRequired` catches failures cleanly and does not spin, keeping retry strictly bounded.

### 8.4 Backend Stale-Cookie Lifecycle
- Dedicated test `TestSecurity_BackendRestartSSEStaleCookieRecovers` proves:
  - Instance 1 SSE connects with cookie 1 (200 text/event-stream).
  - Backend restarts (Instance 2).
  - Old cookie 1 sent to Instance 2 returns `401 Unauthorized`.
  - Client calls `GET /api/v1/auth/session` on Instance 2 to establish cookie 2.
  - Cookie 2 sent to Instance 2 `/api/v1/events` connects successfully (200 text/event-stream).

### 8.5 Local-Process Threat Boundary Review
- **Finding:** A raw local process running under the user's OS account (e.g. Python script, curl, or local binary) can construct HTTP requests with `Host: 127.0.0.1:8080` and `Origin: http://127.0.0.1:8080`, call `/api/v1/auth/session`, extract the session cookie and CSRF token, and invoke protected APIs.
- **Security Boundary Truth:**
  HTTP headers (`Host`, `Origin`) and cookies are browser-enforced isolation primitives. They protect against **untrusted browser origins (malicious websites)** and **DNS rebinding**. They do NOT protect against arbitrary code already executing locally with the user's OS privileges.
  Local process isolation is outside the scope of web origin security and must not be overclaimed.

### 8.6 Truthful Threat Model Matrix

| Scope | Threat Vector | Status | Mechanism |
| :--- | :--- | :--- | :--- |
| **Protected** | Malicious websites calling localhost | **PROTECTED** | `Origin` header rejected (403), `SameSite=Strict` cookies omitted |
| **Protected** | Cross-Site Request Forgery (CSRF) | **PROTECTED** | `X-CSRF-Token` header required on mutating methods (`POST`, `PUT`, `DELETE`) |
| **Protected** | Cross-origin reading of state | **PROTECTED** | CORS strictly rejects foreign origins, `SameSite=Strict` cookie required |
| **Protected** | DNS rebinding via browser `Host` header | **PROTECTED** | Global `ValidateHost` rejects non-loopback hosts with 403 Forbidden |
| **Protected** | Accidental LAN exposure | **PROTECTED** | `CheckNonLoopbackBind` unconditionally rejects non-loopback binds (`0.0.0.0`, LAN IPs) |
| **Protected** | Secret leakage in URLs | **PROTECTED** | Zero authentication credentials accepted in query parameters |
| **Not Protected** | Malware running as local OS user | **NOT IN SCOPE** | Local processes control their own HTTP headers and sockets |
| **Not Protected** | Compromised local operating system | **NOT IN SCOPE** | OS-level compromise supersedes process memory boundaries |
| **Not Protected** | Highly-privileged browser extensions | **NOT IN SCOPE** | Extensions with host permissions can bypass browser origin restrictions |

### 8.7 Complete CSRF Method Audit
- Audited all routes in `internal/api/router.go`. Protected mutating methods used: `POST`, `PUT`, `DELETE`.
- Both `ValidateCSRF` in `internal/api/security.go` (rejecting any non-safe method without valid `X-CSRF-Token`) and `authFetch` in `web/src/api.ts` (injecting `X-CSRF-Token` on `['POST', 'PUT', 'DELETE', 'PATCH']`) provide 100% complete coverage for all mutating HTTP methods.

### 8.8 Absent-Origin Bootstrap Reasoning
- W3C/WHATWG Fetch specifications specify that browsers do not send an `Origin` header on same-origin `GET` requests (e.g., initial SPA load and bootstrap).
- Foreign cross-origin browser requests **always** send an `Origin` header (e.g. `Origin: https://evil.com`), which `ValidateOrigin` rejects with 403 Forbidden.
- Subresource tags (`<script>`, `<img>`) cannot read JSON response bodies due to CORS, cannot read `HttpOnly` cookies, and cannot forge the custom `X-CSRF-Token` header.
- Permitting absent-Origin on `GET /api/v1/auth/session` is standard, required for loopback SPA initialization, and completely secure under the browser threat model.

### 8.9 CSRF-Cookie YAGNI Decision
- `getCsrfToken()` in `web/src/api.ts` checks `cachedCsrfToken` in memory and falls back to reading `document.cookie` (`godownloader_csrf`).
- Retaining `godownloader_csrf` as a non-HttpOnly cookie provides synchronous availability across multiple tabs and module reloads without requiring an asynchronous round-trip. It is kept under YAGNI.
