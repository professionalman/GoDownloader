## 4. Integrated architecture overview (VS)

- **Startup:** `cmd/desktop` uses Wails v3 with a single-instance mutex. `app.New` builds the core in this order: runtime guard (`<db>.runtime.lock`), SQLite and migrations, master key and settings, ToolManager resolution (authenticated managed yt-dlp first), store cleanup, ProcessSupervisor, engine registry (aria2, yt-dlp if available, qB), job Manager, ResourceGovernor and Scheduler. `App.Start` then runs the tracker and `StartBackgroundTasks` (recovery → governor reconstruction → resumed analyses → reconciler → workdir/queue cleanup → scheduler loop → monitor).
- **Transports:** Wails native IPC (`DesktopService`) for desktop; a loopback-only HTTP server for web/server mode.

## 5. Startup / shutdown findings

**B-1 (BLOCKER) — desktop background loops are cancelled immediately after startup.** VS and VT.

```go
// cmd/desktop/main.go:210-215
startCtx, cancelStart := context.WithTimeout(context.Background(), 15*time.Second)
if err := appInstance.Start(startCtx); err != nil { ... }
cancelStart()
```

`App.Start` derives the tracker context from this `ctx` ([internal/app/lifecycle.go](../../internal/app/lifecycle.go)), and `StartBackgroundTasks` passes it to `m.scheduler.Start(ctx)` and `m.monitor.Start(ctx)` ([internal/job/manager.go](../../internal/job/manager.go):256,262) and to the network reconciler (:225). The scheduler loop exits on `ctx.Done()` ([scheduler.go](../../internal/job/scheduler.go):281). The scheduler loop is the only caller of `DispatchQueuedJob`.

**Reproduced (VT):** an overlay probe (`go test -overlay`, no repository change) runs `New → Start(startCtx) → cancelStart()` exactly as `main.go` does. It observed the scheduler loop context `context canceled` and the tracker runner exited; startup logs show `scheduler: failed to list runnable jobs: context canceled`.

**Effect on the desktop build:**

- queued and new downloads (including selected media formats) are never dispatched;
- progress, completion and finalization monitoring stop;
- the network-policy reconciler and tracker refresh stop.

`cmd/server` is unaffected because it passes a process-lifetime context. The line was introduced in `1d1e466` (2026-09-20, Wails shell preview), so it predates V0.9.1 and also affects V0.9.0. No test exercises `cmd/desktop` startup with real context propagation, which is why the full green suite missed it.

**M-4 (MEDIUM) — a hung shutdown has no watchdog.** VS. `RequestQuit` → `App.Shutdown` (5 s context), but `Manager.Stop` is context-free and unbounded (scheduler `wg.Wait`). If it hangs, `wailsApp.Quit()` is never reached and there is no `os.Exit` fallback. The single-instance mutex and runtime lock stay held, so relaunches are forwarded to the stuck instance and exit with code 0; the user must use Task Manager.

**Other (LOW, VS):**

- `Shutdown` errors are discarded after `Run`.
- Recovery runs under the 15 s start deadline, so a slow recovery fails startup.
- A relaunch during the ≤5 s shutdown window is forwarded to the dying instance.

## 6. Single-instance findings (VS; VT: `TestGuard_ContentionSamePath`)

- Second launches are detected by the Wails named mutex and forwarded via `WM_COPYDATA`. The process exits inside `application.New`, before `app.New`, so no second scheduler, ToolManager or ProcessSupervisor starts.
- The runtime guard (share-mode-0 lock on `<db>.runtime.lock`) independently blocks a second runtime on the same database.
- The window is restored via `showMainWindow` unless control flags are present.
- `recordSecondLaunch` only records counters and arguments.

**Bypasses (VS):**

- `--diagnostic-smoke` runs a full second runtime with `downloader_smoke.db` against the **same** `DataDir` (see M-2).
- `--trigger-*`, `--set-*` and `--emit-*` write `diagnostic_command.json`, which the primary polls. Any same-user process can use this file to quit the app or change preferences (LOW).
- LOW (NT): `secondLaunchHandler` and `mainWindow` are written and read across goroutines without synchronization.

## 7. Close-to-tray and restart-required findings

- **Close-to-tray (default true), VS:** closing hides the window and leaves the backend untouched. Tray Quit runs `App.Shutdown` (tracker drain → `Manager.Stop` → ProcessSupervisor shutdown → DB close → guard release), then `wailsApp.Quit()`, and the process exits. A new launch creates a new backend.
- **Restart-required journey:**
  - Install sets `restartRequired=true` and holds the usage gate.
  - Closing to the tray and reopening (or reloading the webview) keeps the in-memory flag, so the update is not falsely activated (VS).
  - Tray Quit ends the process.
  - A new launch has `restartRequired=false`, resolves the authenticated managed binary first, and registers the engine exactly once (`Register` is only called inside `New`; there is no re-exec or in-process restart). VT: `TestApp_RestartRegistersAuthenticatedManagedYtdlp` (real compiled helper executable placed in the ledger store).
  - UI text instructs a complete quit and relaunch (CP2 A-8).
- **NT:** the full GUI journey (real install → tray → relaunch) on a real desktop session.
- **Caveat:** after the relaunch, media downloads still never dispatch because of B-1.

All of the following are VT by the CP2 suites (`internal/toolmanager`, `internal/database`, `internal/app`), rerun green in this audit:

- fresh install with no yt-dlp;
- user-configured and system PATH yt-dlp (remain version-probed and user-owned);
- the legacy managed path (version-probed, untouched);
- authenticated managed resolution and restart;
- already-current;
- newer update;

- invalid or impostor signature;

- network failure classes;
- restart-required;
- the gate refusing activation during analysis or download.

There is no automatic installation and no install triggered by submitting a media URL (VS). Known media hosts never fall back to aria2 (VT, CP1).

**Real-binary acceptance (VT, this audit):** the official `yt-dlp.exe` for `2026.10.26` was downloaded through the release asset API into an isolated scratch directory, never a GoDownloader data directory. Its SHA-256 `f5389d36…7a7d` matched the signature-authenticated digest before execution, and `--version` returned `2026.10.26`, matching the tag the managed path requires.

**L-1 (LOW):** `--version` took about 2.1–2.4 s even warm. User-configured and PATH yt-dlp are probed with the generic **3 s** timeout, so on slower machines or under antivirus first-scan a valid PyInstaller yt-dlp can be reported unavailable (`YT_DLP_UNAVAILABLE`). Managed binaries use 20 s.

## 9. Media workflow findings

- **The lifecycle** `Create → Analyze → AwaitingSelection → SelectFormat → Queued → Downloading → Processing → Completed` and its failure, cancel, retry, restart and queue-persistence branches are VT by the CP1/CP2 suites. On the desktop host, however, *Queued → Downloading* never happens because of B-1.
- **Managed-tool update while jobs exist:** queued jobs stay queued, waiting analyses stay `ANALYZING`, and running jobs are never killed (VT, CP2 A-2).
- **H-2 (HIGH) — the analysis probe is not process-tree-supervised, and the managed binary does spawn descendants.** VS and VT.
  - FND-4B exempted `AnalyzeWithPolicy` (`exec.CommandContext`) on the premise "No descendants spawned".
  - **Experiment (VT, real binary, scratch only):** running the official `yt-dlp.exe` as an analysis probe against an unroutable host produced the tree *root `yt-dlp.exe` → child `yt-dlp.exe` + `conhost.exe`*. Killing only the root, which is what `CommandContext` does on Windows, **left the child `yt-dlp.exe` and `conhost.exe` running** (test processes were cleaned up afterwards).
  - **Consequences:**
    - a cancelled or timed-out analysis, or app Quit during an analysis, leaves an orphaned yt-dlp outside the Job Object;
    - because the child inherits the stdout pipe, `cmd.Output()` blocks until the child exits, so the analysis worker keeps its analysis permit and UsageGate shared use until the orphan finishes.
  - This fails MED-OWN's "complete process-tree supervision" and the SPK07 intent.
  - It is not destructive: analysis uses `--no-download`, and temporary auth files are cleaned after the call returns.

## 10. ResourceGovernor / scheduler findings

- **Composition (VT, CP1/CP2 suites rerun green):** global and per-engine transfer capacity, the media analysis FIFO, FFmpeg pre-admission, scheduler admission, Run Now (cannot bypass limits), Retry, and startup reconstruction (no phantom leases).
- **Exception:** the governor is bypassed by the cancel-during-dispatch race (Section 11, lease released while the engine runs).
- **On desktop:** admission never happens after startup at all (B-1).

## 11. Cross-engine cancellation risk assessment (H-1, HIGH)

**Source (VS):**

- `dispatchQueuedJob` reads the job once, calls `eng.Start`, then persists `DOWNLOADING` with an **unconditional** `repo.Update` from its stale copy ([manager.go](../../internal/job/manager.go):3827-3896).
- `Cancel` on a job it observed as `QUEUED` sees `EngineID == ""`, **skips the engine cancel**, writes `CANCELLED` unconditionally, deletes the queue entry, and calls `removeActive`, which releases the governor lease.

**Deterministic reproducer (VT):** a disposable test file (created, run, deleted; the repository is unchanged) drove real Manager code with interleaving hooks in test doubles:

| Interleaving | Cancel() result | Final DB status | Engine | Lease | Monitor |
|---|---|---|---|---|---|
| (b) Cancel during engine start | `cancelled` | **`downloading`** | started, **never cancelled** | released | tracking |
| (c) Cancel read before dispatch persisted, wrote after | success | **`cancelled`** | started, **never cancelled** | released | **not tracking** |

**Answers:**

| Question | Answer |
|---|---|
| Can a cancelled job begin downloading? | **Yes** (b). |
| Can SQLite report CANCELLED while an engine process is active? | **Yes** (c). The aria2 or yt-dlp download keeps running untracked. |
| Can a queue entry be orphaned? | Not observed: both paths delete it. |
| Can a permit leak? | It inverts: the lease is **released while the transfer runs**, so capacity is over-admitted. |
| qB-managed tasks? | Torrents already carry an `EngineID`, so Cancel does cancel in qB through TOR-EXT ownership checks. The racing dispatch then fails on the removed torrent and can overwrite `CANCELLED` with `FAILED` (VS, not reproduced). Foreign tasks are unaffected because of the TOR-EXT ownership guard. |
| Unwanted filesystem writes? | **Yes** (c): an untracked download continues writing to the destination. |

**Classification:** HIGH, reproducible concurrency corruption. It needs a user cancel at the moment of dispatch.

**Recommendation:** release blocker; fix before V0.9.1. Use the same pattern as G9:

- dispatch commits `QUEUED → DOWNLOADING` by compare-and-set, and cancels the just-started engine if it loses;
- Cancel compare-and-sets on the observed status and re-evaluates on loss.

## 12. Cross-database managed-storage risk assessment

| Mode | DB | DataDir | Shares the store? |
|---|---|---|---|
| Default desktop | `%APPDATA%\GoDownloader\downloader.db` | `…\GoDownloader\data` | — |
| `--diagnostic-smoke` | `downloader_smoke.db` | **same** `…\data` | **yes** |
| Server mode | `DB_PATH` / `--db` | `DATA_DIR` (default `./data`, CWD-relative) | only if an operator deliberately points `DATA_DIR` at the desktop's data directory |
| Tests | temp directories | temp directories | no |

- **Managed binaries (VS + VT):** after CP2, cleanup deletes only binaries its *own* ledger retired. Scratch files are removed only while holding the cross-process acquisition lock. The smoke ledger is empty and never installs, so it cannot delete the desktop's active or LKG binary (`TestAcquisition_CleanupNeverDeletesAnotherLedgersBinaries`).
- A running process cannot lose its LKG through this path. Losing it would require a second database to install the same release twice in the same directory.
- **Decision:** not a release blocker (LOW). Document that `DATA_DIR` must not be shared across databases.

**M-2 (MEDIUM) — smoke mode does damage other shared-DataDir state.** VS. The smoke runtime's startup cleanup removes every marked job workdir under `data/tmp` unknown to *its* database ([storage/service.go](../../internal/storage/service.go)), plus all temporary auth cookie exports ([mediaauth/service.go](../../internal/mediaauth/service.go)). That includes the main instance's **in-flight media work directories** when run concurrently. These are partial temporary files (retryable), not completed downloads. `--diagnostic-smoke` is an operator diagnostic referenced by the V0.9.0 release-gate procedure; the installer and app never invoke it.

**Fix:** give smoke mode an isolated `DataDir`.

## 13. HTTP / Wails security findings (VS + VT)

- **Wails:** native IPC only. No HTTP listener exists in `cmd/desktop` (searched for `ListenAndServe`, `net.Listen` and `http.Server`).
- **HTTP server:** refuses non-loopback binds unconditionally (`CheckNonLoopbackBind` before `ListenAndServe`).
- **Tool mutation routes:** wrapped in `RequireAuthenticatedSensitiveAction`. They are refused for every caller under `DISABLE_AUTH`, and otherwise pass session, CSRF and origin checks (VT: `TestToolsAPI_InstallRefusedWhenAuthDisabled`, `TestToolsAPI_RequiresSessionAndCSRF`).
- **Public DTOs:** carry no paths, URLs or tokens (VT: `TestToolsAPI_AuthenticatedResponsesArePathFree`). Signed CDN query strings are never logged (VT: `TestAcquisition_LogsNeverContainSignedCDNTokens`).

No transport-specific bypass was found.

## 14. Installer packaging results

All VS (build-script and metadata inspection). The installer was **not executed** (NT).

- **Chain:** `task package` → `windows:package` → `build:native` (`-tags production`, `buildinfo.Version=0.9.1`) → `makensis build/windows/installer.nsi`.
- **Architecture and identity:** amd64 only (aborts on non-x64). Entrypoint `GoDownloader.exe`. Versions agree on 0.9.1 across ldflags, `info.json`, manifest and NSIS (guarded by `cmd/desktop/version_consistency_test.go`). LOW: `main.go` still describes the app as "Windows Desktop Technical Preview".
- **Scope:** per-user, `%LOCALAPPDATA%\Programs\GoDownloader`, HKCU uninstall key, `asInvoker`.
- **Payload:** a single `File` directive (`GoDownloader.exe`) plus the uninstaller and a shortcut. **No yt-dlp, FFmpeg, qBittorrent or aria2 binary is embedded.** The only `go:embed` content is icons, `web/dist`, and the *public* yt-dlp signing key.
- **Uninstall (script logic):**
  - removes the exe, uninstaller, empty install directory, shortcuts, the HKCU key, and the Run value only on an exact match;
  - **preserves `%APPDATA%\GoDownloader`**, including the database, managed tools and the default `downloads` folder;
  - refuses to run while the runtime lock is held.
- **Upgrade:** overwrites in place. There is no version comparison and no downgrade guard (LOW).
- **B-2 (BLOCKER, release process) — the installer artifact is stale.** `bin/GoDownloader-0.9.1-beta-windows-amd64-setup.exe` was built 2026-10-04 and predates TOR-EXT closure (`bac2c90`), MED-OWN CP1 (`e0c0047`) and CP2 (`7b44c1e`). Handing it out would ship a build without any of this work. It must be rebuilt from the corrected commit.
- **M-5 (MEDIUM):** binaries are built with `-buildvcs=false` and no commit injection, so a shipped exe cannot be traced to a commit.
- **Signing:** every artifact is unsigned (`Get-AuthenticodeSignature`: `NotSigned`). The roadmap defers this to the RC, so it is acceptable for a private Beta and blocks public distribution.

## 15. WebView2 readiness

## 19. Provenance / license findings — public-distribution blocker assessment

All VS. **P-1: public distribution BLOCKED.**

- There is no root `LICENSE`, `NOTICE` or third-party notice file.
- `README.md` states "This project is for personal use" (with a "license-personal_use" badge).
- ROADMAP lines 97–106 and 394 make a formal license/provenance posture a gate for **any public redistributable Beta**.

**Dependencies needing attribution or notices:**

- `github.com/ProtonMail/go-crypto` (BSD-3-Clause), `cloudflare/circl` (BSD-3-Clause), `golang.org/x/*` (BSD-3-Clause);
- `anacrolix/torrent` (**MPL-2.0**, file-level copyleft: a source-availability notice is needed);
- `mattn/go-sqlite3` (MIT; SQLite public domain), `wails/v3` (MIT), `gorilla/mux` and `google/uuid` (BSD-3-Clause), `rs/cors` (MIT);
- npm: React (MIT), lucide (ISC), Tailwind (MIT).

None of these notices are bundled; the installer packages only the exe.

**yt-dlp:**

- The pinned signing key provenance is recorded (CP2).
- The Windows `yt-dlp.exe` is a **GPLv3+ combined work** per the upstream README. It is acquired at runtime from upstream, not bundled, but there is no in-app or installer disclosure.

**Other:**

- WebView2 is not redistributed, so its redistribution terms do not apply.
- Publisher is "GoDownloader", not a legal entity.
- Unsigned (Section 14).

**Assessment:**

- A **private/internal** Beta is permitted under the roadmap.
- **Any public Beta is blocked** until the owner establishes the license and provenance posture, bundled notices (including MPL-2.0), and a GPLv3+ disclosure for the runtime-acquired yt-dlp.

This is an engineering assessment, not legal approval.

## 24. Narrow correction recommendations (not implemented in this audit)

1. **B-1:** start the runtime with a process-lifetime context, cancelled only in `Shutdown`, and keep any startup deadline local to the synchronous recovery step. Add a `cmd/desktop` startup test asserting the scheduler loop is alive after `Start` returns, and that a queued job dispatches.
2. **H-1:** compare-and-set transitions for dispatch (`QUEUED → DOWNLOADING`; on a lost CAS, cancel the just-started engine and release the lease) and for Cancel (CAS on the observed status; re-evaluate on loss), mirroring G9. Turn the two interleavings in Section 11 into permanent regression tests.
3. **H-2:** run the analysis probe through `ProcessSupervisor.StartOwned` (Job Object), keeping its bounded timeout, and correct FND-4B's exemption premise. Add a Windows test asserting no descendant survives cancellation.
4. **H-3:** record the SPK-SYN3-07 acceptance (FND-4B plus the H-2 fix as evidence) and obtain owner acceptance of the yt-dlp inventory/provenance gate (CP2 §28 provides the inventory facts).
5. **B-2:** rebuild the installer via `task package` from the corrected, committed tree, with commit provenance injected (M-5).
6. **M-2:** give `--diagnostic-smoke` its own `DataDir`.
7. **M-1:** check WebView2 via `EdgeUpdate\Clients\{F3017226-…}` `pv` (non-empty and not `0.0.0.0`) or ship the evergreen bootstrapper, and show an in-app message when the runtime is missing.
8. **M-3:** surface FFmpeg (and FFprobe) status and diagnostics in Settings → Dependencies, and resolve FFprobe.
9. **M-4:** add a bounded shutdown with a hard-exit fallback.
10. **M-7:** enable CI (including `-race`) on `dev`, or provision a race-capable environment.
11. **P-1 (before any public distribution):** owner-chosen license, bundled third-party notices (including MPL-2.0), GPLv3+ disclosure for the runtime-acquired yt-dlp, and code signing per the roadmap.
