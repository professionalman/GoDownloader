# V0.9.1 Packaging Path Safety Closure

**Scope:** close one packaging defect. The NSIS step did not use the selected binary output directory, so it could package a stale executable and overwrite an unrelated installer. This covers no architecture, runtime or feature changes, no installer release, and no governance approval.

**State:** uncommitted on `dev`. Nothing was staged, committed, pushed, tagged, released or distributed.

Evidence labels: **SRC** = source inspection; **SCRIPT** = script test against disposable files (real NSIS where noted); **NSIS** = real end-to-end packaging run; **CI** = GitHub Actions.

## 2. Confirmed root cause (SRC + SCRIPT)

How the selected output directory (`BIN_DIR`) flowed through `windows:package` before the fix:

| Step | Path used | Follows `BIN_DIR`? |
|---|---|---|
| 1. Desktop build ([build/windows/Taskfile.yml](../../build/windows/Taskfile.yml)) | `-o "{{.BIN_DIR}}/{{.APP_NAME}}.exe"` | Yes |
| 2. NSIS invocation | `makensis build/windows/installer.nsi`, with **no `/DBIN_DIR`** | **No** |
| 3. NSIS `File` ([build/windows/installer.nsi](../../build/windows/installer.nsi)) | `${BIN_DIR}\GoDownloader.exe`, with `BIN_DIR` defaulting to `..\..\bin` (resolved from the script's folder, i.e. the repository's `bin\`) | **No** |
| 4. Installer output | `OutFile "${BIN_DIR}\…-setup.exe"`, the same default | **No** |
| 5. Manifest ([build/windows/write-build-manifest.ps1](../../build/windows/write-build-manifest.ps1)) | `{{.BIN_DIR}}/…` | Yes |
| 6. Hashing | The manifest's artifact list | Yes |

**Consequence:** with an overridden `BIN_DIR`, NSIS packaged whatever executable sat in the repository's `bin\` (possibly stale or foreign) and **overwrote** the installer there. The manifest then refused, because no installer existed in `BIN_DIR`, but only **after** the overwrite.

With the default `BIN_DIR` (`bin`) the two locations coincided, which is why the candidate built from a clean clone was correct. Revert-to-fail (Section 5) reproduces the defect: with the pre-fix script and invocation, NSIS wrote into the default folder and packaged its executable.

## 3. Source changes

- **New [build/windows/package-installer.ps1](../../build/windows/package-installer.ps1).** It:
  1. resolves `-BinDir` to an absolute path, refusing if the directory is missing;
  2. refuses before NSIS runs if `GoDownloader.exe` is missing from it;
  3. locates `makensis` (PATH or the standard install folders);
  4. invokes `makensis "/DBIN_DIR=<absolute dir>" installer.nsi`;
  5. fails on a non-zero NSIS exit;
  6. requires the installer to exist in that same directory and to have been written by this run.
- **[build/windows/installer.nsi](../../build/windows/installer.nsi).** The `..\..\bin` default is replaced with `!error` when `BIN_DIR` is undefined, so no invocation can silently fall back to another folder. The payload (`File` / `OutFile`) is unchanged.
- **[build/windows/Taskfile.yml](../../build/windows/Taskfile.yml).** The package step calls the script with `-BinDir "{{.BIN_DIR}}"`, the same value the build and manifest steps use.

No developer-machine path is hardcoded. No third-party binary is added. The manifest script is unchanged.

## 4. Default and custom output behaviour

| Case | Behaviour |
|---|---|
| Default (`BIN_DIR=bin`) | Unchanged result: executable, installer and manifest in `<repo>\bin\` |
| Custom directory, including spaces | Executable, installer and manifest all in the selected directory; the default folder is neither read nor written |
| Missing output directory | Refused before NSIS; nothing is created |
| Missing executable | Refused before NSIS; existing files untouched |
| `makensis` without `/DBIN_DIR` | Compile error; nothing is packaged or overwritten |

## 6. Actual NSIS packaging run (NSIS)

The full `wails3 task windows:package GO_TRIMPATH=-trimpath BIN_DIR="<scratch>\custom out dir"` ran in a fresh clone at `e894253` with this fix applied. MSYS2 was first on PATH for that process only (see [V0.9.1_INSTALLER_CANDIDATE_ACCEPTANCE](V0.9.1_INSTALLER_CANDIDATE_ACCEPTANCE.md) for the toolchain finding). Results:
- exit 0, with "Installer packaged" and "Build manifest written";
- NSIS `Output:` was the custom directory (with spaces);
- all three artifacts are there;
- the installer is 6,960,153 bytes, i.e. the real 17,418,240-byte executable, not the clone's 13-byte decoy;
- the decoy executable and installer planted in the clone's default `bin\` were **byte-identical** afterwards;
- the manifest SHA-256 values match the files.

Because the fix is uncommitted, that build is correctly labelled `dirty: true` / `releaseCandidate: false`. It is a test run, not a candidate.
