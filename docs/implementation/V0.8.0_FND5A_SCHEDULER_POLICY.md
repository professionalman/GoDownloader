## 1. Executive Summary

FND-5A introduces deterministic priority aging, stable FIFO tie-breaking, one-shot Run Now overrides, and dynamic `not_before` / `retry_count` lifecycle management to GoDownloader's durable core scheduler without adding unnecessary schema columns, periodic database writes, or abstract policy hierarchies.

Prior to FND-5A, GoDownloader's scheduler operated on a static partition where High-priority jobs could indefinitely starve Normal- and Low-priority work, no aging mechanism existed, Run Now was unimplemented, and `not_before` / `retry_count` columns (added in FND-1) had no runtime writers or clock-injected eligibility evaluation.

FND-5A establishes:
1. **Deterministic Bounded Aging:** A monotonic aging function derived from durable enqueue timestamps that guarantees starvation resistance (low-priority jobs waiting > 40 minutes outrank newly arrived high-priority jobs) while strictly preserving user manual ordering within the same priority lane (`ReorderQueue`).
2. **One-Shot Run Now Override:** Modeled cleanly and durably by placing the job at `position = 0` and clearing `not_before = nil`. Run Now provides immediate dispatch precedence while strictly respecting `max_concurrent_downloads` capacity limits. On dispatch, the override is automatically consumed when the queue row is deleted.
3. **Dynamic Eligibility Seam:** An injected evaluation clock seam (`ClockFunc`) on `Scheduler` and `SQLiteQueueRepository.NextRunnable` allowing deterministic testing of aging, retry delays, and restart consistency without real long sleeps.
4. **StateSync & Security Compliance:** All queue mutations (`RunNow`, `SetJobPriority`, `ReorderQueue`, `ScheduleRetry`) emit sequenced `EventJobUpdated` events, advance the global event cursor, and remain protected behind FND-3A session authentication, CSRF, and origin/host validation.

## 2. Current Scheduler Map

The scheduling lifecycle in GoDownloader operates as follows:
- **Persistence:** Table `job_queue` in SQLite stores `job_id`, `position`, `action` (`'start'` or `'resume'`), `retry_count`, `not_before`, `enqueued_at`, and `updated_at`.
- **Lanes & Positions:** Priorities are represented by `jobs.priority` (`'high'`, `'normal'`, `'low'`). `NextPosition(ctx, priority)` returns `MAX(position) + 1` for that lane. Manual reordering (`ReorderQueue`) writes positions `1, 2, ..., N` in a single transaction.
- **Dispatch Loop:** `Scheduler.loop()` runs in a single goroutine listening on non-blocking `kickCh`. `schedule()` counts running jobs (`CountDownloading()`) plus in-flight reservations against `getLimit(ctx)` (`max_concurrent_downloads`, default 3).
- **In-Flight Claim:** `reserveInFlight(jobID, action)` tracks active dispatches in a mutex-protected map. If a job is already in flight, the scheduler avoids tight loops and duplicate dispatch.
- **Dispatch Execution:** `dispatchSingle()` delegates to `Manager.DispatchQueuedJob()`. Upon starting, the job transitions to `StatusDownloading` and its `job_queue` row is deleted.
- **Failures & Requeue:** Failed dispatches transition the job to `StatusFailed` (or `StatusPaused` if resume action) and remove the queue row. Retrying a job enqueues a fresh entry with incremented `retry_count`.

## 4. Ponytail & YAGNI Architecture Decisions

1. **No Abstract Policy Hierarchy:**
   Avoided creating `ISchedulerPolicy`, `IAgingStrategy`, or `IPriorityCalculator` interfaces. All policy calculation is implemented as pure, cohesive Go functions in `internal/job/policy.go`.
2. **Zero Schema Migrations (Reusing Existing Columns):**
   - Did NOT add a `run_now BOOLEAN` column. Reused `job_queue.position = 0` as the Run Now sentinel.
   - Reused existing `retry_count` and `not_before` columns added during FND-1.
   - Run Now override is naturally consumed on dispatch when the queue row is deleted.
3. **No Background Periodic Database Updates:**
   - Effective aging scores are NOT written to SQLite every minute on a ticker.
   - Effective priority is computed on-the-fly at dispatch time from durable enqueue timestamps.
4. **Lightweight Clock Seam:**
   - A single `ClockFunc func() time.Time` on `Scheduler` and variadic `evalTime ...time.Time` on `IQueueRepository.NextRunnable` allows tests to advance time deterministically without sleeps or heavy clock frameworks. Existing single-argument callers continue to compile without change.
5. **No ResourceGovernor in FND-5A:**
   - Permitted transfers, disk permits, weighted semaphores, and wait reasons are deferred to FND-5B.

## 5. Final Priority Model & Deterministic Aging Policy

### Base Priority Numerical Mapping
- `JobPriorityHigh` ("high"): `200`
- `JobPriorityNormal` ("normal"): `100`
- `JobPriorityLow` ("low"): `0`
- Unspecified / default: `100`

### Deterministic Aging Formula
$$\text{effective\_priority} = \text{base\_priority} + \min\left(\left\lfloor \frac{\max(0, \text{now} - \text{enqueued\_at})}{\text{aging\_interval}} \right\rfloor \times \text{points\_per\_interval}, \text{max\_aging\_bonus}\right)$$

Default configuration:
- `AgingInterval`: $60\text{ seconds}$ ($1\text{ minute}$)
- `AgingPointsPerInterval`: $5\text{ points}$
- `MaxAgingBonus`: $250\text{ points}$

### Starvation Resistance Proof
- Initial arrival ($t = 0$): High = 200, Normal = 100, Low = 0. High wins.
- At $t = 21\text{ min}$: Low reaches $0 + (21 \times 5) = 105 > 100$, outranking brand new Normal jobs.
- At $t = 41\text{ min}$: Low reaches $0 + (41 \times 5) = 205 > 200$, outranking brand new High jobs.
- Normal at $t = 21\text{ min}$: reaches $100 + (21 \times 5) = 205 > 200$, outranking brand new High jobs.
- When High and Low arrive concurrently at $T_0$, High also ages ($200 + \text{bonus}$) and stays exactly 200 points ahead of Low. High is never unfairly overtaken by Low when both have waited equally.

### Preservation of Explicit User Queue Order
Within the same priority lane (`a.Job.Priority == b.Job.Priority`), explicit queue position strictly governs:
1. `a.Position < b.Position`
2. `a.EnqueuedAt < b.EnqueuedAt`
3. Lexicographical `JobID` tie-breaker.
This guarantees that manual reordering via `ReorderQueue` is never overridden by timestamp aging within the lane.

## 6. Run Now Semantics & State Lifecycle

- **Precedence:** Run Now jobs (`position <= 0`) have absolute precedence over non-Run Now jobs, regardless of base priority or aging.
- **Multiple Run Now FIFO:** Tied Run Now jobs break ties by lower `Position` -> earlier `UpdatedAt` -> earlier `EnqueuedAt` -> stable `JobID`.
- **Capacity Adherence:** Run Now does NOT start downloads beyond `max_concurrent_downloads`. If capacity is full, the job waits at the front of the queue (`position = 0`) and is dispatched immediately when a slot frees.
- **Delay Clearing:** Invoking Run Now on a retry-delayed job explicitly clears `not_before = nil`, making it immediately runnable.
- **State Validation:**
  - `StatusQueued`: Valid. Updates position and timestamps.
  - `StatusPaused`: Valid. Unpauses to `StatusQueued`, action set to resume, positioned at 0.
  - `StatusDownloading`, `StatusProcessing`, `StatusSeeding`: Rejected with 409 Conflict (`ErrInvalidJobState: job is already active`).
  - `StatusCompleted`, `StatusCancelled`: Rejected with 409 Conflict (`cannot run completed/cancelled job`).
  - `StatusFailed`: Rejected with 409 Conflict (`cannot run failed job; use retry`).
- **Override Consumption:** When the job is dispatched, `Scheduler.dispatchSingle()` deletes the `job_queue` row. The one-shot override is consumed.

## 7. `retry_count` & `not_before` Lifecycle

- **`retry_count`:**
  - Fresh enqueues start with `retry_count = 0`.
  - Manual `Retry(ctx, id)` and `ScheduleRetry(ctx, id, delay)` increment `retry_count` based on existing queue records or execution attempt counts (`m.execRepo.GetLatestExecution`).
  - Successful dispatch deletes the queue row, resetting state for subsequent fresh lifecycles.
- **`not_before`:**
  - Filtered at the database query layer: `(q.not_before IS NULL OR q.not_before <= ?)`.
  - Future `not_before` jobs remain visible in `GET /api/v1/queue` (`QueueSnapshot`) with their timestamp.
  - As time advances past `not_before`, jobs become runnable automatically without database mutation.

## 14. Final Total-Ordering & Run-Now State Verification

### Previous Comparator Inconsistency & Concrete A/B/C Cycle
In the initial FND-5A implementation, `CompareQueuedJobs` branched on whether the two candidates shared the same base priority:
- If `a.Job.Priority == b.Job.Priority`, it evaluated `Position` first before timestamp.
- If `a.Job.Priority != b.Job.Priority`, it evaluated `EffectivePriority` first.

This pair-dependent branching violated transitivity and produced a comparison cycle on the concrete candidate set:
- **Candidate A:** Priority = Low (base 0), Position = 2, aged 50m to `EffectivePriority = 250`.
- **Candidate B:** Priority = Normal (base 100), Position = 1, newly enqueued, `EffectivePriority = 100`.
- **Candidate C:** Priority = Low (base 0), Position = 1, newly enqueued, `EffectivePriority = 0`.

Pairwise evaluations under the old comparator produced:
1. $A$ vs $B$ (different lanes): Effective rank compares $250 > 100 \implies A < B$ ($A$ wins).
2. $B$ vs $C$ (different lanes): Effective rank compares $100 > 0 \implies B < C$ ($B$ wins).
3. $C$ vs $A$ (same lane, Low): Compared position first, so $1 < 2 \implies C < A$ ($C$ wins).

Result: $A < B \land B < C \land C < A$ — a comparison cycle violating strict weak ordering and transitivity.

### Final Globally Consistent Precedence Chain
To guarantee a mathematically strict weak order (irreflexive, asymmetric, and transitive), the comparator now applies a single, globally consistent precedence chain across all candidate pairs without branching based on base priority equality:
1. **Run Now Status:** Any candidate with `Position <= 0` outranks non-Run Now candidates.
2. **Multiple Run Now Tie-Breaker:**
   - Lower `Position` (e.g. `-1 < 0`)
   - Earlier `UpdatedAt` (first requested Run Now wins)
   - Earlier `EnqueuedAt`
   - Stable `JobID` lexicographical comparison (`strings.Compare(a.JobID, b.JobID)`)
3. **Effective Priority:** Higher effective priority (`base + aging contribution`) wins.
4. **Base Priority:** Higher base priority score breaks ties between equal effective priorities (e.g. newly arrived Normal at 100 beats aged Low at 100).
5. **Durable Queue Position:** Lower manual queue `Position` breaks ties between equal effective and base priorities.
6. **Durable Enqueue Timestamp:** Earlier `EnqueuedAt` breaks position ties.
7. **Stable JobID:** Lexicographical comparison as the deterministic final tie-breaker.

Under this unified chain, for the concrete set:
- $A$ vs $B$: $250 > 100 \implies A < B$ ($A$ wins)
- $B$ vs $C$: $100 > 0 \implies B < C$ ($B$ wins)
- $A$ vs $C$: $250 > 0 \implies A < C$ ($A$ wins)
- Sorted order: $[A, B, C]$ consistently and deterministically. Transitivity holds: $A < B < C$.

### Manual Reorder Tie Semantics
Manual queue position is strictly preserved as a **tie-breaker** for candidates of equal effective scheduling rank. When two candidates in the same lane have equal effective priority, `Position 1` beats `Position 2`. Manual position does not bypass aging to overtake a genuinely higher effective rank, thereby eliminating cycles while preserving explicit user queue ordering.

### Permutation-Determinism Result
Sorting 10 distinct non-trivial permutations (rotations, reversals, and swaps) of a mixed candidate set containing Run Now, aged Low, fresh High, and Normal jobs with `RankQueuedJobs` yielded the identical canonical `JobID` ranking in every iteration (`TestRankQueuedJobs_InputPermutationDeterminism` passed). Candidate retrieval order from SQL never leaks into scheduling precedence.

### Multiple Run Now Behavior & Durability Across Reopen
When multiple jobs are marked Run Now, the earlier requested Run Now job wins based on `q.updated_at` recorded during `RunNow`. In `internal/database/queue_repository.go`, `scanQueuedJob` was updated to scan `q.updated_at` directly into `qj.UpdatedAt` (with fallback to `j.UpdatedAt`).
- `TestSchedulerPolicy_Q_MultipleRunNowDeterministicOrder` verified that Job A (requested first) dispatches before Job B when concurrency capacity is 1.
- `TestSchedulerPolicy_R_MultipleRunNowSurvivesDBReopen` verified that closing and reopening the SQLite database preserves this deterministic selection.

### Run Now / ReorderQueue Interaction
When `ReorderQueue` is executed for a priority lane, it assigns positions $1 \dots N$ to the specified jobs in that lane. This operation **intentionally consumes and overrides** any Run Now sentinel (`position = 0`) for jobs included in the reordered lane, reflecting the user's latest explicit manual ordering intent (`TestSchedulerPolicy_S_ReorderQueueOverridesRunNow` passed).

### Paused Run Now Actual Lifecycle
Tracing the paused Run Now lifecycle verified end-to-end scheduler dispatch:
1. Job is paused with `Status = StatusPaused` and existing engine correlation (`EngineID`).
2. `Manager.RunNow(ctx, id)` is called:
   - Sets queue entry `Position = 0`, `NotBefore = nil`, and sets `Action = QueueActionResume`.
   - Transitions job status in DB from `StatusPaused` to `StatusQueued`.
   - Emits sequenced `EventJobUpdated` and kicks the scheduler.
3. Scheduler's `NextRunnable` queries `WHERE j.status = 'queued' AND (q.not_before IS NULL OR q.not_before <= :now)`. The paused job is returned as the top runnable candidate due to `position = 0`.
4. Scheduler claims the job and executes `DispatchQueuedJob(ctx, qj)`:
   - Since `qj.Action == QueueActionResume`, it invokes `eng.Resume(ctx, j)`.
   - Job transitions to `StatusDownloading`.
   - The queue row is deleted from `job_queue`.
5. Verified by `TestSchedulerPolicy_T_PausedRunNowActuallyDispatches` which asserts that `fakeEng.Resume` is called, status becomes `StatusDownloading`, and the queue entry is removed.

Active states (`downloading`, `processing`, `seeding`) and terminal states (`completed`, `cancelled`, `failed`) are strictly rejected with `ErrInvalidJobState` (`TestSchedulerPolicy_U_RunNowRejectsActiveAndTerminalStates` passed).

### Retry Count Dequeue/Requeue Durability
When a job is dispatched by the scheduler, its `job_queue` row is deleted. To prevent `retry_count` from resetting to 1 upon dispatch failure, `dispatchQueuedJob` now records a durable `JobExecution` attempt in `IExecutionRepository` before queue deletion:
- An initial run records attempt number 1.
- If a job with `retry_count = N` is dispatched, it records attempt number $N+1$.
- Upon failure, when `Manager.Retry` or `Manager.ScheduleRetry` is invoked, it consults `execRepo.GetLatestExecution(ctx, j.ID)` as the durable source of truth, assigning `retry_count = exec.AttemptNumber` ($N+1$).
- `TestSchedulerPolicy_V_RetryCountSurvivesDispatchFailureRequeue` verified that a job queued with `retry_count = 1`, dispatched (queue row deleted), and failed, obtains `retry_count = 2` upon retry.
- `TestSchedulerPolicy_W_RetryCountDurableAcrossDBRestart` verified that closing and reopening the database preserves `retry_count = 2` and allows subsequent retries to advance to 3.

### StateSync Verification
- Mutating operations (`RunNow`, `SetJobPriority`, `ScheduleRetry`, `ReorderQueue`) emit `EventJobUpdated` through `m.publish(EventJobUpdated, j)`.
- `m.publish` internally advances the global event cursor via `m.AdvanceEventCursor(context.Background())`.
- Redundant secondary calls to `m.AdvanceEventCursor(ctx)` in `RunNow` and `ScheduleRetry` were removed, guaranteeing exactly one monotonic cursor advancement per mutation.
- Pure ranking evaluations (`CompareQueuedJobs`, `RankQueuedJobs`, `SelectNextRunnable`) do not emit events or advance cursors.
