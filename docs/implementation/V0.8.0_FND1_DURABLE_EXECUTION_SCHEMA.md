## 7. Migration Strategy & Failure Model

- **Safe Forward Migration:** Runs automatically inside `database.New()` via `db.migrateToV08Fnd1()`.
- **Atomic Transaction:** Entire migration is wrapped in a single SQLite transaction (`tx, err := db.conn.Begin()`). If any statement fails, `tx.Rollback()` is executed, leaving the database unmodified and without the `'v08_fnd1_migrated'` marker.
- **Idempotency:** Protected by `app_settings.v08_fnd1_migrated` and `PRAGMA table_info` checks. Repeated calls succeed without error or duplicate modification.
- **Data Preservation:** Tested against real V0.7.2 fixtures. Existing jobs, queue entries, torrent jobs, torrent files, categories, app settings, encrypted secrets, and tracker sources are preserved without loss.

## 12. Final FND-1 Review / Lock

### Migration Backup Decision
- **Posture:** ROADMAP.md line 362 specifies: *"Back up before every semantic migration."*
- **Implementation:** Integrated pre-migration backup directly into `DB.migrateToV08Fnd1()` in [`internal/database/sqlite.go`](file:///C:/Users/bkkav/Downloads/downloader/internal/database/sqlite.go).
- **Mechanism:** When `hadExistingFile` is true (detected prior to `sql.Open`) and `v08_fnd1_migrated` is 0, GoDownloader executes SQLite's native `VACUUM INTO '<dbPath>.pre-v08.bak'`.
- **Properties:** Atomic, self-contained, flushes uncheckpointed WAL frames, requires zero external dependencies, leaves destination file closed immediately, and preserves the exact pre-migration state on disk even if subsequent DDL or binary execution fails.
- **Testing:** Verified by `TestV08Migration_FromRealV072Fixture` (asserts `.pre-v08.bak` exists, non-empty, and contains pre-migration schema) and `TestV08Migration_TransactionRollbackOnFailure` (asserts backup is preserved even when migration rolls back).

### Checkpoint Cardinality Invariant
- **Invariant:** An HTTP checkpoint is **Job-scoped durable transfer state that survives/rebinds across execution attempts**.
- **Key Relationships:**
  - `http_checkpoints`: Primary key is `job_id`. Holds a nullable foreign key `execution_id REFERENCES job_executions(id) ON DELETE SET NULL`.
  - `http_checkpoint_segments`: Composite primary key is `(job_id, segment_index)` with `FOREIGN KEY (job_id) REFERENCES http_checkpoints(job_id) ON DELETE CASCADE`.
- **Multi-Attempt Behavior:**
  - Attempt 1 creates checkpoint and segments tied to `job_id` and references `execution_id = attempt1.ID`.
  - On failure, attempt 1 completes as failed. The checkpoint and on-disk staging artifact remain intact.
  - Attempt 2 (retry/resume) queries checkpoint by `job_id`. If remote validators match, attempt 2 updates `execution_id = attempt2.ID` and resumes progress without data loss.
  - If remote resource mutates (e.g. ETag change), attempt 2/3 calls `SaveHTTPCheckpoint` with new validator state and fresh segments; `SaveHTTPCheckpoint` atomically deletes all stale segments for `job_id` and inserts the new segment topology.
- **Testing:** Verified by `TestExecutionRepository_HTTPCheckpointMultiAttemptRebindAndReset`.

### Repository Cohesion Decision
- **Evaluated Boundary:** `IExecutionRepository` / `SQLiteExecutionRepository` covering execution attempts, HTTP checkpoints, finalization records, tool records, and event cursors.
- **Classification:**
  - *Execution attempts:* COHESIVE WITH EXECUTION LIFECYCLE
  - *HTTP checkpoints:* COHESIVE WITH EXECUTION LIFECYCLE
  - *Finalization records:* COHESIVE WITH EXECUTION LIFECYCLE
  - *Tool ledger:* ACCEPTABLE TEMPORARY PERSISTENCE BOUNDARY (3 methods; separate repository rejected under Ponytail/YAGNI until ToolManager in FND-4)
  - *Event cursors:* ACCEPTABLE TEMPORARY PERSISTENCE BOUNDARY (2 methods; separate repository rejected under Ponytail/YAGNI until StateSync in FND-2)
- **Decision:** NO CODE CHANGE REQUIRED. A single cohesive repository avoids interface noise while providing a single persistence home for all execution-level foundations.

## 13. Backup Retry Idempotency Verification

### Behavior Before Review
- Prior implementation unconditionally executed `os.Remove(backupPath)` before `VACUUM INTO`.
- While this ensured `VACUUM INTO` would not encounter a "file exists" error, it had the flaw of destroying the original pristine V0.7.2 pre-migration backup taken before the initial failure.

### Verified Next-Start Scenario
1. V0.7.2 database exists.
2. Initial startup executes `VACUUM INTO '<database>.pre-v08.bak'`, successfully creating a pristine snapshot.
3. Migration transaction fails partway (e.g. schema collision, process termination, disk failure).
4. Transaction rolls back cleanly; `v08_fnd1_migrated` marker is absent in `app_settings`.
5. `<database>.pre-v08.bak` remains on disk and is non-empty.
6. Application/DB is reopened without any manual user intervention or file deletion.
7. FND-1 migration retries.

### Ponytail / YAGNI Policy & Code Changes Made
In [`internal/database/sqlite.go`](file:///C:/Users/bkkav/Downloads/downloader/internal/database/sqlite.go):
- Inspected `backupPath` using `os.Stat(backupPath)`.
- If `backupPath` already exists and `fi.Size() > 0`, it is recognized as a valid pre-migration snapshot from a prior attempt: GoDownloader **reuses and preserves** the original backup, bypassing `VACUUM INTO` entirely.
- If `backupPath` does not exist or has `fi.Size() == 0` (e.g. created by a killed process before write), it is cleaned up and recreated via `VACUUM INTO`.
- When the migration succeeds, `v08_fnd1_migrated` is recorded in `app_settings`.
- On any subsequent application startup, the pre-migration check `SELECT COUNT(*) FROM app_settings WHERE key = 'v08_fnd1_migrated'` detects that migration is already complete and returns immediately at line 118, completely bypassing backup handling and DDL.

## Backup Validity Verification

### Previous Size-Only Behavior
- The initial retry logic checked only `os.Stat(backupPath)` with `Size() > 0`.
- This proved file existence and non-zero length, but not that the file was a usable SQLite database. A truncated file, corrupt write, non-SQLite payload, or partial failed `VACUUM INTO` would be treated as valid protection.

### Final Validity Rule
- Implemented `database.IsUsableSQLiteBackup(path string) bool` in [`internal/database/sqlite.go`](file:///C:/Users/bkkav/Downloads/downloader/internal/database/sqlite.go).
- To be recognized as a valid pre-migration backup:
  1. The file must exist and have `Size() > 0`.
  2. The file must successfully open via SQLite.
  3. `PRAGMA quick_check` must execute cleanly and return `"ok"` (validating all page structures, cell offsets, free lists, and b-trees).
  4. The file must contain the core pre-migration `jobs` table (`SELECT COUNT(*) FROM sqlite_master WHERE type='table' AND name='jobs' > 0`).

### Invalid-Backup Behavior & Failure Ordering
- If `<database>.pre-v08.bak` is missing, 0 bytes, or fails SQLite integrity verification:
  1. GoDownloader does **not** silently treat it as valid protection.
  2. The invalid file is removed and recreated via `VACUUM INTO` from the still-unmigrated main database (demonstrably safe since `v08_fnd1_migrated` is uncommitted).
  3. The newly recreated backup is immediately verified with `IsUsableSQLiteBackup`.
  4. If backup recreation or integrity verification fails, migration **fails closed** immediately before `tx.Begin()`, ensuring **zero semantic migration DDL is executed** on the main database.
  5. If an existing backup is valid, it is preserved byte-for-byte and never overwritten.
