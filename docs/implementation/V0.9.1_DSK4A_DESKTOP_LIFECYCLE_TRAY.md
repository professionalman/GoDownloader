- With the only window destroyed, `wailsApp.Run()` returned immediately.

### 7. New Close-to-Tray Behavior

- `mainWindow.RegisterHook(events.Common.WindowClosing, ...)` routes events to `lifecycle.HandleWindowClosing(e, mainWindow)`.
- If `ShouldHideOnClose()` evaluates to `true` (tray is available and application is not quitting):
  1. Calls `e.Cancel()` to abort window handle destruction.
  2. Calls `mainWindow.Hide()` to hide window from desktop and taskbar.
  3. `wailsApp.Run()` remains blocked in its message loop.
  4. Backend runtime, job manager, and `ProcessSupervisor` continue execution without interruption.
  5. `App.Shutdown` is **NOT** called.

### 8. Tray Configuration & Wails Registration Semantics

- **Configuration vs. Synchronous Shell Registration:**
  - In Wails v3 (`v3.0.0-beta.23`), `wailsApp.SystemTray.New()` and `tray.SetIcon()` configure the tray object in memory and queue it for initialization.
  - They do **not** synchronously verify shell registration with Windows Explorer. Shell registration occurs asynchronously when `wailsApp.Run()` starts the message loop and `windowsSystemTray.show()` calls `ShellNotifyIcon(NIM_ADD, &nid)`.
  - To remain strictly truthful to Wails API semantics, the lifecycle coordinator tracks `trayConfigured` rather than asserting synchronous shell visibility.
- **Wails Failure and Recovery Semantics:**
  - If `ShellNotifyIcon(NIM_ADD)` fails on startup (e.g. Explorer shell not yet running or restarting), Wails logs a warning (`initial systray add failed`) and continues without crashing.
  - Wails listens for the Windows message `TaskbarCreated` (`RegisterWindowMessage("TaskbarCreated")`). Whenever Windows Explorer starts or restarts, Wails invokes `reshowSystrays()`, calling `s.show()` to re-add the notify icon automatically.
  - During icon updates (`updateIcon`), if `ShellNotifyIcon(NIM_MODIFY)` fails (icon dropped due to Explorer crash), Wails logs a warning, rolls back `currentIcon`, and does not crash or panic.
- **Dual-Layer Recovery Invariant:**
  - *Primary Recovery:* Left-clicking the Windows notification area tray icon or selecting `Show GoDownloader` from the tray context menu restores and focuses the window.
  - *Secondary Safety Fallback:* If the tray icon is temporarily obscured in overflow, hidden, or Explorer is restarting, launching GoDownloader again triggers single-instance argument forwarding, which executes `showMainWindow(mainWindow)` to restore and focus the existing window without creating a headless orphan or duplicate core.
  - *Configuration Fallback:* If `wailsApp.SystemTray` is unavailable (`trayConfigured == false`), `ShouldHideOnClose()` returns `false`, allowing normal window close and deferred application shutdown.

### 10. Host Lifecycle State

Defined in `cmd/desktop/lifecycle.go`:
```go
type DesktopLifecycle struct {
    quitting       atomic.Bool
    trayConfigured atomic.Bool
    mu             sync.Mutex
    app            *app.App
    wailsApp       *application.App
    mainWindow     *application.WebviewWindow
    shutdownCount  int32
    trayShowCount  int32
    trayQuitCount  int32
}
```
- Distinguishes user close (`!quitting && trayConfigured` $\rightarrow$ hide) from real application termination (`quitting || !trayConfigured` $\rightarrow$ allow close).
- Reuses `internal/app.App`'s existing concurrent join and idempotent shutdown without duplicating state machines.
- Tracks diagnostic counters `trayShowCount` and `trayQuitCount` for verifiable, deterministic testing.

---

### 11. Quit Ownership

- All application quit paths converge on the single coordinator `DesktopLifecycle.RequestQuit()`:
  - Real Windows Tray Context Menu: `Quit GoDownloader`.
  - Desktop Service: `DesktopService.Quit()`.
  - Diagnostic CLI: `--trigger-quit`.
- `RequestQuit()` atomically sets `quitting = true` via `quitting.Swap(true)`:
  - Any subsequent or concurrent quit calls return immediately.
  - Shuts down `appInstance.Shutdown(ctx)` (stopping manager, supervisor, and closing DB).
  - Calls `wailsApp.Quit()` to break the event loop.

---

### 12. App.Shutdown Interaction & Defer Safety Net

- When `wailsApp.Quit()` breaks the event loop, `wailsApp.Run()` in `main.go` returns.
- The deferred `appInstance.Shutdown(shutdownCtx)` executes as a safety net.
- Because `internal/app/lifecycle.go` implements strict idempotency (`if a.stopped { return a.shutdownErr }`), the second call returns immediately with zero error and zero redundant teardown.
- If the application terminates via an unhandled path (e.g. tray failure fallback), the deferred `Shutdown` ensures clean database closure and child process cleanup.

### 13. ProcessSupervisor & Child Process Behavior

- **Composed Verification (DSK-4A Lifecycle):**
  - Source inspection of `DesktopLifecycle.HandleWindowClosing` proves that hiding the window only calls `e.Cancel()` and `mainWindow.Hide()`. It **never** invokes `App.Shutdown()`, `job.Manager.Stop()`, or `ProcessSupervisor.Shutdown()`.
  - Because the supervisor remains alive and active, Win32 Job Object handles remain valid, and owned child processes (e.g. `yt-dlp`) continue transferring or muxing media without interruption.
- **Locked FND-4 ProcessSupervisor Proof:**
  - 22 focused tests in `downloader/internal/process` verify child process management:
    - `TestSupervisor_A_SimpleChildStartsAndExitsNormally` & `TestSupervisor_E_ProcessIsolation` prove child processes continue normal execution while the supervisor remains alive.
    - `TestSupervisor_D_ShutdownTerminatesAllTrees` proves that on `ProcessSupervisor.Shutdown`, closing the Job Object causes the Windows kernel to enforce `KILL_ON_JOB_CLOSE`, cleanly terminating all child process trees without orphan leakage.
- **Quit Integration:**
  - Real Tray Quit routes directly through `DesktopLifecycle.RequestQuit()` $\rightarrow$ `App.Shutdown()` $\rightarrow$ `ProcessSupervisor.Shutdown()`, guaranteeing complete termination of owned child processes on exit.

### 16. Second-Instance Hidden Restore

- When a secondary process is launched, Wails single-instance mutual exclusion executes inside `application.New()`.
- The secondary process forwards its CLI arguments and CWD to the primary instance, then exits with code 0 in under 70ms.
- The primary instance's `OnSecondInstanceLaunch` executes:
  - Records forwarded arguments.
  - Invokes `showMainWindow(mainWindow)`, calling `Show()`, `Restore()`, and `Focus()`.
  - The hidden window returns to view without reconstructing backend core or reloading frontend DOM.
